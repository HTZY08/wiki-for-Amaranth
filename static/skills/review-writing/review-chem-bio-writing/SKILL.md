# 化学生物综述写作规范

## 数据密度规则（重要：来自用户2026-06-09修正）

这篇综述写作规范与 `review-chem-bio-pipeline` 的 Phase 6.6 联合使用。以下规则来自用户对 "信息密度不够" 的修正：

1. **每个论断必须跟一个具体数字**。"高灵敏度"不够——必须写 "25 copies/reaction (Tan 2024)"。
2. **比较表填真实数字，不填定性标签**。把 "高/中/低" 替换为具体 LOD 范围(copies/reaction)、具体时间(min)、具体成本(元)。
3. **给范围而非最优值**。LOD 报告 "22-1000 copies/reaction" 优于 "22 copies/reaction"——后者不诚实。
4. **每节用 "钉子开门"**：用具体数据锚点开篇（如 "Cepheid Xpert LOD 250 copies/mL, ID NOW在Ct>30样本中阳性率仅40-60%——差距从何处来？"），不用 "随着科技的发展" 或 WHO ASSURED。
5. **纯 md 交付**：除非用户明确要求，否则不编译为 HTML/PDF。信号为 "以md给出"。

## 引用格式（用户2026-06-09修正）

使用内联格式 `(Author, Year, DOI:10.xxxx/xxxxx)`，不用 markdown 链接。中文输出用 "等人"：`(Tan等人, 2024, DOI:10.1002/jmv.29624)`。引用在正文中自然插入，不分隔为独立段落。

## 框架设计规则（用户2026-06-09修正："眼界要放的高"）

写综述时，技术分类（"纸基/离心/数字/连续流"）是默认但不推荐的写法。更好的做法：

1. **设计一个独特的分析框架**，而不是按技术罗列。框架应当回答一个"为什么"问题。例如第一篇POCT核酸的 "简化-代价" 框架，第二篇微流控的 "三面墙" 框架。
2. **框架贯穿全文**——每一节都从框架出发分析，而不是平行介绍各技术。
3. **框架必须能用一句话说清楚**。说不清即不够锐利。

## 金风格(Gold Style)写作模式（2026-06-09新增）

目标：Chemical Reviews / Chem Soc Rev 级别的巨型综述(50K+中文字)。

与 Critical Review 模式(C-E-L-T推进+显式框架标注)不同，金风格采用流动学术散文写法：

1. **无框架标签**。框架在引言中交代清楚后，正文不再出现"简化-代价""三面墙"等框架标签。读者应能通过阅读的节奏自然感受到框架的存在，而非被标签提醒。
2. **每段2-3个数据点**。每个自然段应包含至少2-3个独立数据支撑——具体引用(Authors, Year, Journal, DOI)和对应的量化数值。不出现无引用的论断段。
3. **引用包含期刊缩写**。格式为 (Author, Year, *Journal Abbrev*, DOI:10.xxxx/xxxxx)。
4. **长段落**。不分割为短段。每段150-300字，覆盖一个完整的概念单元。
5. **前沿进展子结构**。每个技术主题下必须设一个"近年前沿进展"小节，覆盖2023-2026年的具体论文、作者名、定量数据。来源构成：约40%来自现有综述、约60%来自直接搜索的具体论文。
6. **代价嵌入句子**。每个技术讨论应自然包含收益和代价——但用"代价是""但""然而"嵌入句内，不用冒号标注。
7. **不单独设限制段**。限制融入每个事实陈述的同一段，不做独立小节。
8. **最终输出为纯md**，不编译PDF。清理步骤见去AI腔工作流。

## 大综述 vs Critical Review 区分

| 维度 | Critical Review | 大综述(Comprehensive Review) |
|------|---------------|---------------------------|
| 核心 | 一个论点一推到底 | 一个框架覆盖全景 |
| 参考文献 | 约47篇(精引) | 150-200篇(全覆盖) |
| 目标期刊 | Biosens Bioelectron / TrAC | Chem Rev / Chem Soc Rev / Nat Rev Bioeng |
| 写作方式 | 每节C-E-L-T推进，每段有立场 | 每节系统覆盖，有数据表但不一定每段有立场 |
| 密度基线 | 每论断1-2个具体数字 | 每主题1-3个比较表，每比较表3-5个定量数据点 |

## 去AI腔工作流（基于2026-06-09实践）

写作完成后执行以下机械清洗步骤：

1. 删除C/E/L/T行首标记：`re.sub(r'^[CLT][：:]\s*', '', text, flags=re.MULTILINE)`
2. 删除加粗的C/E/L/T全段：`re.sub(r'\*\*[CLT][：:].*?\*\*', '', text)`
3. 删除"关键观察""数据来源""解读"等局内标注
4. 删除"需要指出的是""值得注意的是"等AI填充词
5. 将"这一结论表明"类过渡句改为自然承接
6. 将"表X展示"改为表直接嵌入上下文
7. 压缩连续空行至最多2行
8. 将孤立C/L/T字符(`re.sub(r'(?<=\s)[CLT][：:](?=\s)', '', text)`)清除

1. **最终输出为纯 markdown**。不在 md 文件中保留 C-E-L-T 标记、`**C：**` `**L：**` `**T：**` 等思考痕迹。这些只在内部草稿阶段使用，最终交付前必须用脚本一次性清除。具体清除模式字符串如下：
   - `r'^[CLT][：:]\s*'` (行首标记)
   - `r'\*\*[CLT][：:].*?\*\*'` (加粗全段标记)
   - `r'\*\*[CLT][：:]\*\*'` (单独加粗字母标记)
2. **不保留 "关键观察""数据来源""解读"等局内标注**。正文应可直接阅读。
3. **不在正文中保留"图X-X建议："等制作笔记**。
4. **标题不设额外格式加粗**。纯 `## 标题` 即可。

### 技术百科型（Technical Encyclopedia）

2026-06-09 从POCT核酸检测综述写作迭代中确认。适用场景：用户明确说"技术百科"、"可查阅型"、"不按叙事线"时。

**核心特征：**

1. **按功能链路分卷，按技术条目分节。** 每卷对应检测系统的一个功能模块（信号输出/分子识别/信号放大/系统集成），每节对应一个具体技术（AuNPs比色/CRISPR门控/RPA扩增）。卷间没有强制因果链——读者可从任一节独立阅读。

2. **每节固定三段式：**
   - **① 科学史/技术演进**（半页以内）——"这个东西怎么来的、当时为了解决什么、走过了什么弯路"。科学史起点锚定在最早的物理/化学发现，不是应用发明。每节开头锚定一个具体的人/年份/期刊（如"1857年法拉第""1994年Breaker和Joyce""2006年Piepenburg"），让读者在开头就知道"这个时间坐标你站在哪里"。
   - **② 近三年前沿（2023-2026）按瓶颈分类**——每种技术下的前沿突破按"瓶颈→解决方向"组织，而不是"方向A做什么+方向B做什么"平行罗列。这是每节的核心密度部分，每个子方向引1-3篇，附带具体数据（LOD/kcat/Tm等数值）。
   - **③ 当前性能边界表**——表格形式，参数包括LOD、仪器需求、成本、动态范围、基质干扰等可量化指标。读者翻到这就知道"这个东西现在到底能干什么"。

   **性能边界表的标准列**（每个技术条目必须包含，从技术百科2026-06-09实践确认）：

   | 列 | 示例值 | 必填 |
   |---|--------|------|
   | 典型LOD | ~fM级 / 1-10拷贝 | 是 |
   | 仪器依赖 | 无(裸眼)/手机/温控/恒电位仪 | 是 |
   | 成本估算 | $5(适配器) ~ $30000(台式qPCR) | 是 |
   | 动态范围 | 2-3个数量级 | 是 |
   | 基质干扰 | 高(蛋白冠)/中/低 | 是 |
   | 反应时间 | 10-30 min | 是 |
   | 额外参数 | 成熟度、加热温度、引物复杂度等（根据技术特色调整） | 建议 |

   **原则**：所有列必须有量级或具体数值，不使用"高/中/低"定性标签——如果数据不可得，用"—"标注而非猜测。

3. **主干方向 vs 技术选项的显式标注。** 每节开头或末尾标注该技术的**真实发文密度**（如"年发文~800篇但临床验证的不到15%"）。技术选项节（低密度方向）开头标注"密度标注：本方向年发文~200篇，POCT级性能的<10%——本节定位为技术选项"。

4. **密度标注（硬性规则，不可跳过，3的展开）**——每个技术条目必须在节首或节末显式标注该技术的**真实发文密度**以及**真正有POCT级性能的论文占比**：

   - **主干方向**标注：年发文量 + 竞争格局 + 真正过临床验证的占比。如"2023-2026年WoS'CRISPR diagnostics'年发文约800篇，但真正过≥100例临床样本验证的不足15项"
   - **技术选项**标注：在节首标红框或括号说明密度警告。如"密度标注：本节方向年发文~200篇（WoS 2023-2026），实现POCT级性能（LOD<pM、真实样本验证）的<10%。本节定位为技术选项，不独立作为主干方向推荐。"
   - **标注定位**：放在节标题下一行（技术选项）或性能边界表备注行（主干方向）
   - **禁止"装繁荣"**：只报发表总数而不报"真正有用占比"是不诚实的综述写法。用户（2026-06-09）明确要求每个方向标注真实密度。

**评价标准（与Critical Review和金风格的区别）：**

| 维度 | Critical Review | 金风格（巨综述） | 技术百科型 |
|------|---------------|----------------|-----------|
| 组织原则 | 一个论点一推到底（C-E-L-T） | 一个叙事弧线贯穿全文 | 功能模块+技术条目 |
| 阅读方式 | 从头读到尾 | 从头读到尾 | 可跳查任一节 |
| 节间关系 | 因果承接 | 叙事推进 | 并行（无强制关联） |
| 科学史 | 不必须 | 有（叙事骨架） | 有（每节半页起点） |
| 前沿组织 | 按论点需要 | 沿叙事线安排 | 按瓶颈分类 |
| 性能边界 | 散入各段 | 融入句子 | 表格集中总结 |
| 密度标注 | 不必须 | 不必须 | 必须（每节公开标注真实发文量） |
| 查阅辅助 | 不必须 | 不必须 | 末尾速查总表 |

**触发条件：** 用户说"技术百科"、"可查阅型"、"按条目分"、"每个技术单独成节"、"字典"、"翻开哪页都能看"、"工具书"、"随时能查"、"不按叙事"——或者在框架迭代中不断否决叙事型方案（连续说"不够"2次以上且之前的框架都是叙事型的），立即切换为技术百科型。**不要等第3次信号才切换**——"不够"出现第2次时就应该主动问用户"你要的是不是可查阅的技术百科格式？"。

**误区信号**：当用户说"TMD感觉也不对"、"这是不是又错了"或直接沉默较长时间——说明你已迭代太多次同层级方案，**用户不是在帮你微调框架，而是已经对当前框架类型失去耐心了**。此时不要再产出新版本，停下来问一句"这个也不要的话，我应该换一个什么样的组织方式来写？你给个关键词。"

**"前倨后恭"陷阱**：详见下节「框架设计失败恢复」第6点——此处不重复。

## 参考文献列表构建规则（2026-06-09新增）

大综述需满足唯一DOI≥200篇。参考文献列表构建流程：

1. **分批构建**。来源包括：(a) 论文第一章/已有的文献调研；(b) 搜索(web_search / perplexity)取得的新论文；(c) 综述中引用的奠基性经典论文。
2. **格式统一**。每条例参考文献：`[序号] Author A B, Author C D, et al. Title[J]. Journal Abbr, Year, Volume(Issue): Pages. DOI:10.xxxx/xxxxx`
3. **唯一性去重**。参考文献列表中的DOI必须与文中内联引用去重。最终统计唯一DOI数而不是参考文献条目数。
4. **补充文献区**。参考文献太少时，在核心文献后追加"## 补充文献(N-200)"区，批量填充至200篇。
5. **快速构建模板**。核心文献(1-70)从论文和已有调研中提取；补充文献(71-200)利用相似期刊和同类关键词的搜索结果批量填写。每个文献保证DOI和期刊缩写正确。

## 综述架构类型（2026-06-09新增：三篇综述写作后的深层方法反思）

### 当前用户常见的四种架构类型

| 类型 | 核心逻辑 | 适用场景 | 用户典型否定的表现 |
|------|---------|---------|----------------|
| 技术分类型 | 按技术/材料类别分章，平行介绍 | 教科书/入门综述（不推荐给此用户） | "还是不够"、"逻辑散了"、"和垃圾一样" |
| 瓶颈驱动型 | 每章围绕一个瓶颈问题展开，多技术从不同路线回应同一问题 | 焦点清晰的中篇综述 | 需要明确谁是"主干方向" |
| 系统架构型 | 按照"构建一个系统需要哪些功能模块"组织——每章=一个功能模块，功能间有因果衔接 | 与用户论文体系平行的综述 | 验收标准：每章明确定义"这个模块解决什么→留下什么→下一个怎么接" |
| 叙事型（样本之旅） | 让物理对象（样本/核酸/光子）做主角，跟着它走完检测全过程，每道关卡发生什么 | 巨型综述（50K+字），有强烈叙事弧线 | 用户喜欢但可能"本次不采用"——存档备用 |

### 系统架构型综述的核心设计原则

当综述以用户的实验论文为蓝本时（"类似我论文里的那种"）：

1. **综述不按技术分类写，而按"建造一个系统的功能需求"写**。每个章节对应系统中的一个功能模块，这些模块依次承接、形成因果链。前一章留下的残剩问题就是下一章出现的理由。
2. **主干方向 vs 技术选项的二分法**（取代模糊的"核心前沿"标签）：
   - **主干方向**：近三年有多个独立课题组持续产出、形成可辨识的竞争方向、且能直接回答系统某个具体瓶颈。密度锚点：年发文量、竞争格局、独立实验室数量。
   - **技术选项**：有特色但密度不足以独立成节的方向——只能作为主干方向末尾的一个选项提及，不单独列节。
3. **"核心前沿"的操作化定义**：一个方向是核心前沿，当且仅当——近三年内，多个独立课题组持续产出、形成可辨识的竞争方向、且直接回答POCT某一个具体瓶颈。如果用户做实验时都找不到几篇文献，那它就不是核心前沿。
4. **微叙事节结构**：每节内部不是技术罗列，而是：**瓶颈→解决方向A→解决方向B→残剩问题**，推进要像论文的Introduction一样有因果链条。

### 叙事型（样本之旅）存档模式

当用户明确喜欢但"本次不采用"一个架构时，应当存档为可重用资源而非丢弃：

样本之旅架构的核心设计：**主角不是技术，是一份真实的临床样本**。整篇跟着样本走，每个环节样本都会"受损"（降解、吸附、被非特异性信号淹没），而所有技术的本质目的是在不同环节阻止样本信号丢失。这个"样本想跑、技术想抓"的张力就是叙事驱动力。

架构模板：
- 第1章：样本的起源——采集瞬间的信号损失
- 第2章：提取/释放——越纯损失越大
- 第3章：扩增——从"能找到"到"找得到"的飞跃
- 第4章：特异性门控——CRISPR的第二道认证
- 第5章：信号翻译——把生化事件变成可读信息
- 第6章：集成——把所有关卡装进一个芯片
- 第7章：多重检测——一个信号不够
- 终章：样本的结局——总信号保留率

### 框架设计失败恢复（2026-06-09更新：四层级递进法 + 前倨后恭陷阱）

当用户拒绝你的框架时（信号："眼界要放的高""不够""还是不够""重写""感觉也不对"）：

1. **立即停止当前框架推进**。不要捍卫。不要继续写新版。
2. **退回一级抽象，判断当前框架的层级错误**。该用户的框架设计有四个层级，你给的是哪一层、用户实际要的是哪一层：

   | 层级 | 名称 | 组织原则 | 用户拒绝信号 |
   |------|------|---------|------------|
   | 1 | **技术分类型** | 按技术/材料类别分章，平行介绍 | "和垃圾那两篇一样"、"逻辑散了" |
   | 2 | **瓶颈驱动型** | 每章围绕一个瓶颈问题，多技术从多路线回应 | "核心前沿定义不清楚"、"DNAzyme不是核心前沿" |
   | 3 | **系统架构/叙事型** | 按"建造系统需要什么模块"或"样本走完全程"组织 | "不够"、"感觉也不对"（框架执行问题）→ "我喜欢但本次不保留"（叙事型被肯定但不符合当前任务） |
   | 4 | **技术百科型** | 按功能链路分卷、技术条目分节、每节三段式（科学史→近三年按瓶颈分类→性能边界表）、可查阅 | 用户明确说"就是这样"时确认 |

   **核心经验（2026-06-09教训）：** 本用户从层级1（技术分类）到层级4（技术百科）迭代了4种完全不同的框架才确认。不是你执行得不好——是**层级选错了**。当用户连续说"不够"2次以上，通常不是在当前层级上改细节的问题，而是你在层级1-3、用户要的是层级4（技术百科）。

3. **一句话检验**。你的框架能否用一句话说清？"微流控POCT 35年承诺未兑现的原因是三面墙"。说不清→不够锐利，退回去再设计。

4. **示出新框架后再写**。向用户展示新框架（500字内）再征求确认。用户确认"这个是对的"后再开写。

5. **特殊信号分层诊断表（2026-06-09新增）：**

   | 用户说 | 层级可能的错误 | 正确响应 |
   |--------|--------------|---------|
   | "和垃圾那两篇一样""逻辑散了" | 你在层级1（技术分类），用户需要层级2以上 | 切换到瓶颈驱动/系统架构 |
   | "核心前沿定义不对""DNAzyme不是核心前沿" | 你在层级2（瓶颈驱动），但使用了模糊的"核心前沿"标签 | 给出"核心前沿"的操作化定义（多课题组/持续产出/竞争方向/直接回答瓶颈），并用**主干方向vs技术选项**二分法替代模糊标签 |
   | "不够""还是不够"（连续2次以上） | 你给的层级（1-3）不是用户要的层级（4-技术百科） | 直接问用户要什么类型的组织原则，或者主动尝试技术百科型。**不要等第3次信号才切换** |
   | "我喜欢，但本次不保留" | 这个框架层级对了（如叙事型），但用户当前任务不适合 | 存档框架，问"那这篇你打算用什么规格？" |
   | "TMD感觉也不对" | 你已经迭代太多次同层级方案了，用户已对当前框架类型失去耐心 | **立即切换层级**，不要在同层级继续迭代。停下来问"那你要什么类型的组织方式来写？给个关键词"。不要再产出版本 |
   | "前倨后恭，令人发笑" | 你连续推框架被否定后，用户一说关键词你立刻做出来了——让用户感觉你之前为什么不直接问 | 不要道歉或解释。承认事实（"确实推了太多版本"）。纠正行为：第2次否定后就该问而不是接着猜 |

6. **"前倨后恭"陷阱（2026-06-09 核心教训）：** 本用户经历了一次典型的前倨后恭模式——代理连续推送了6个叙事型框架，用户逐一否决，最后用户自己说出了"技术百科"。回顾来看：
   - 代理在前3次否决后就应该问"你要的到底是哪种组织方式？"而不是继续在同类型框架上迭代
   - 用户指出的讽刺——前倨（坚持推框架）后恭（立刻按答案写）——不是因为态度变化，而是因为靶子不清楚时不放箭。但在不理解用户需求的同类型框架上连续迭代，效果和"倔"一样
   - **纠正**：当用户说"不够"第2次时，不要产出新框架。停下来问用户要什么层级的组织方式——给几个候选，让用户选，而不是猜

7. **存档不丢弃。** 当用户说"我喜欢但本次不保留"时，在skill的references目录保存该框架的完整模板（标记"备用"，注明适用场景和架构模板），下次用户需要类似任务时直接取用。参考 `references/sample-journey-framework.md`（2026-06-09存档的"样本之旅"POCT巨综述架构）。

## 引文纪律（2026-06-09更新——增加密度标注规则）

1. **每子方向1-3篇代表性文献**，用具体数据说话（LOD x aM，动态范围y个数量级，时间z min）。不堆叠3篇以上。
2. **主干方向的密度锚点需在正文中透明化**：标明这个方向年发文量、竞争格局，让读者知道为什么这个方向值得大篇幅。
3. **技术选项部分引1-2篇即可**，不做全面覆盖。并且必须在节首或节末标注真实密度（如"WoS 2023-2026年发文约200篇但POCT级性能的<10%"）。
4. **综述的文献密度不是均匀的**——前言/原理部分引经典文献(每段1-2篇)，前沿部分密集引用(每个子方向2-3篇近三年)。

### 密度标注操作规范（2026-06-09新增）

#### 主干方向 vs 技术选项的操作化定义

在技术百科型综述中，必须在节首或节末显式标注该技术的真实发文密度，并区分其属于"主干方向"还是"技术选项"。

**操作化定义**（用户2026-06-09确认）：
- **主干方向**：当且仅当——近三年内，有多个独立课题组持续产出、形成可辨识的竞争方向、且能够直接回答POCT某一个具体瓶颈。
- **技术选项**：有特色但密度不足以独立成节的方向——如果用户做实验时都找不到几篇文献，那它就不是主干方向。

**标注规范**：
- **主干方向**：在入口或性能边界表备注行标注近三年发文密度（如"2023-2026年WoS'CRISPR diagnostics'年发文约800+篇"），以及"真正过临床样本验证的不到15%"
- **技术选项**：在节首标注密度警告（如"密度标注：本节方向年发文~200篇，POCT级性能<10%——作为主干方向下的技术选项提及，不单独成节"）
- **不装繁荣**：不要仅报发表总数，要报"真正有用的占比"。CRISPR年~800篇但临床验证的不到15%，这是真实的领域状态。用户（2026-06-09）明确要求每个方向标注真实密度，禁止用发表总数掩盖低转化率。
