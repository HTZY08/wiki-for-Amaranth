# GLM-OCR — 0.9B 轻量多模态文档理解的极简工程

**发布日期：** 2026-03-15（arXiv 提交，已有 300 万+下载）
**来源：** https://arxiv.org/abs/2603.10910
**工程范式：** 用小模型做"确定性任务"的极致效率优化——多 token 预测 + 布局预分析 + 并行识别，在 0.9B 参数下超越大多数大模型

## 设计哲学

OCR/文档理解是一个**确定性结构化生成**任务——输入是图像，输出是已知格式（Markdown、JSON）。传统做法是上大模型（7B+），但 GLM-OCR 揭示了另一个路径：**任务结构已知时，模型不需要大，架构需要精**。

核心约束只有一句话：在 0.9B 参数内实现生产级文档理解，支持高并发和边缘部署，同时比大模型更快更好。

设计出发点是三个观察：
1. 小模型在处理复杂版面时易出现幻觉和重复生成 → 引入显式版面分析模块分解问题
2. 文档解析和关键信息提取都可以统一为结构化生成 → 共享生成框架，参数复用
3. OCR 是确定性的 → 标准的逐 token 自回归解码效率极低 → MTP（多 token 预测）

放弃了什么：
- 放弃了大模型路线（7B+），选择 0.9B 紧凑架构
- 放弃了端到端版面理解，选择两阶段管线（版面分析 + 并行识别）
- 放弃了标准自回归解码，选择 MTP（10 tokens/步训练，平均每步生成 5.2 tokens）

## 关键架构决策

### 模型组成
- **CogViT 视觉编码器（400M）：** 大规模图像-文本数据训练的专用视觉编码器
- **GLM 语言解码器（500M）：** 自回归语言模型，条件于视觉嵌入和文本提示
- **总参数量：** 0.9B，可运行在 vLLM/SGLang/Ollama 上

### MTP（多 Token 预测）
- **训练：** 每步预测 10 个 token
- **推理：** 平均每步生成 5.2 tokens → 约 50% 吞吐提升
- **显存优化：** 跨草稿模型的参数共享，大幅降低额外 GPU 显存
- **核心洞察：** OCR 的强局部依赖性（表格标签、Markdown 语法）使 MTP 特别有效——"broken tags"显著减少

### 两阶段管线
1. **版面分析：** PP-DocLayout-V3 检测结构化区域（标题、表格、公式、段落等）
2. **并行识别：** 不同区域的 GLM-OCR 推理并行执行

### 训练策略
- 多阶段训练逐步对齐视觉-语言表示
- 结构化生成能力增强
- SFT + RL 联合优化

## 关键结果

**文档解析（OmniDocBench v1.5）：** 94.6 —— 所有评测模型中排名第一

**文本和公式识别：**
- OCRBench (Text)：94.0
- UniMERNet：96.5

**表格解析：**
- PubTabNet：85.2
- TEDS：86.0

**关键信息提取：**
- Nanonets-KIE：可比于显著更大的通用多模态模型
- Handwritten-Forms：同

**工业场景：**
- 真实场景表格识别：91.5
- 印章识别：90.5
- 收据 KIE：94.5

**解码效率：** 标准自回归 vs MTP → 吞吐提升约 50%（平均 5.2 tokens/步 vs 1 token/步）

## 范式对比

**vs DeepSeek-OCR (1B+ 参数)：** DeepSeek-OCR 使用更大的视觉编码器和 LLM 解码器，参数量更大但 GLM-OCR 在 OmniDocBench 上以 0.9B 规模超越了 DeepSeek-OCR

**vs MinerU/Marker：** 这些是工具链方案（非端到端模型），依赖传统 OCR 引擎 + 后处理规则。GLM-OCR 的端到端多模态方案在处理复杂版面（公式混排、彩色表格、印章覆盖文字）上有代差优势

**vs GPT-5/Gemini 等通用多模态大模型：** 通用大模型在文档解析上不差，但成本（API 单价、延迟）远高于 GLM-OCR。关键在于：**文档理解是一个不需要通用推理能力的任务，用通用模型是过度杀戮**

## 可复用的工程经验

1. **为确定性任务放弃端到端：** 版面分析前置+并行识别后置的两阶段管线在小规模模型上显著优于纯端到端方案。核心原因是小模型容量不足以同时建模版面结构和内容识别
2. **MTP 的参数共享：** MTP 的额外显存开销通过跨草稿模型参数共享来控制。这个设计决策使 MTP 从"实验中好用但代价高"变成"生产可接受"
3. **结构统一的收益：** 将文档解析和 KIE 统一为结构化生成框架，让模型学到更通用的文档表示，提高了参数效率
4. **不要用通用模型做专用任务：** GPT-5 和 Gemini 能 GLM-OCR 不能的事情很多，但 GLM-OCR 能的事——以 0.9B 参数、50% 吞吐提升、90%+ 准确率——通用模型做不到这个成本效率比
5. **适配主流推理框架从第一天开始：** vLLM/SGLang/Ollama 支持让 GLM-OCR 能够快速渗透到生产环境，技术优势迅速转化为实际部署
