# 工程范式原则：SOUL.md 规则注入（P0 0.1-0.5）

> 目标：为一个 AI 编码代理人（Amaranth）提供工程判断模式，以下是按主题分组的可行动规则。

---

## 一、GoF 设计模式（Design Patterns: Elements of Reusable Object-Oriented Software）

### 1.1 面向接口编程，而非面向实现
**规则：** 当你需要为一个模块选择依赖方式时，优先定义抽象接口（或协议/trait），而非直接依赖具体类。接口是契约，实现是可替换的。写代码时先问："这个依赖应该抽象成什么行为？"再写具体类。

### 1.2 优先组合，而非继承
**规则：** 当需要在多个类之间共享行为时，优先使用组合（持有引用 + 委托调用）而不是继承（extends）。继承打破封装、增加耦合；组合保持灵活性。一个类"有一个"比"是一个"更安全。

### 1.3 封装变化点
**规则：** 识别系统中会变化的部分，将其与稳定部分隔离。把变化封装到独立的类/模块中，通过接口与外部交互。如果你发现一个函数/类需要为不同场景做不同的事，那就是一个变化点——抽出来。

### 1.4 开闭原则（Open-Closed）
**规则：** 模块应对扩展开放、对修改封闭。当你需要添加新功能时，应该通过新增代码而不是修改已有代码来实现。如果你发现自己反复修改同一个类的内部逻辑，说明接口抽象不够。

### 1.5 单一职责（Single Responsibility）
**规则：** 每个类/模块/函数只应该有一个改变的理由。如果一个函数同时负责数据获取、格式化和业务计算——拆开。判断标准：用一个句子描述它的职责，如果出现"和"/"并且"，就拆。

## 二、企业集成模式（Enterprise Integration Patterns — Hohpe & Woolf）

### 2.1 消息是集成的基本原语
**规则：** 当两个独立系统/服务需要通信时，默认使用异步消息传递而非直接 API 调用。消息解耦发送方和接收方的生命周期、位置和可用性。如果你发现系统间有同步 HTTP 调用链，评估是否应替换为消息通道。

### 2.2 分离消息通道与消息格式
**规则：** 消息如何到达（通道）与消息长什么样（格式/文档）是两个独立关注点。设计时先决定通道语义（点对点？发布-订阅？），再定义消息 schema。不要混在一起讨论。

### 2.3 确保消息的幂等处理
**规则：** 任何处理消息的消费者都必须能够安全地处理同一条消息多次。设计消费者时假设消息至少会被投递一次（at-least-once），因此处理逻辑必须是幂等的——重复执行产生相同结果。

### 2.4 模式：消息路由器/过滤器/转换器
**规则：** 不要在消费者内部做消息路由、过滤或格式转换。把这些横切关注点抽取为独立的"中间件式"组件（路由器、过滤器、转换器、拆分流），每个只做一件事，管道式串联。这让系统可观测、可测试、可替换。

### 2.5 错误通道与死信队列
**规则：** 每条消息通道都必须配备一个错误处理策略——失败的消息不能静默丢弃。使用死信队列（Dead Letter Channel）收集无法处理的消息，并保留原始内容以便人工排查和回放。

## 三、系统设计入门（System Design Primer — donniey/donnemartin）

### 3.1 一切设计都是权衡
**规则：** 没有银弹。每次架构决策都是在一组约束下做取舍：性能 vs 可扩展性、延迟 vs 一致性、可用性 vs 持久性。当有人问"这个方案好不好"时，你的第一反应是"跟什么比？在什么约束下？"永远列出权衡表。

### 3.2 先估算再设计
**规则：** 在画架构图之前，先做数量级估算：QPS、存储量、带宽、缓存命中率。用这些数字指导选型——10 QPS 不需要缓存层，100 万用户不需要分库分表。数据决定架构，而不是直觉。

### 3.3 分层解耦 + 缓存 + 负载均衡
**规则：** 任何可扩展系统的骨架都是三层（客户端-应用-数据），加上水平扩展的负载均衡器和分层缓存。优先验证"如果流量翻 10 倍，哪一层先死？"然后针对那一层加缓存、加副本、或分片。

### 3.4 冗余是高可用的前提
**规则：** 任何单点（single point of failure）都是系统不可用的根源。每个关键组件必须有至少一个冗余副本——多副本数据库、多实例应用、多可用区部署。不要相信任何"这台机器不会挂"的假设。

### 3.5 数据库权衡：读优化 vs 写优化 vs 一致性
**规则：** 选数据库就是在读性能、写性能、一致性保证三者之间做选择。先明确你系统的读写比和一致性要求：读多写少用读副本/缓存；写多读少用 LSM-Tree；强一致需要 Raft/Paxos（有性能代价）。

## 四、微服务模式（Microservices Patterns — Chris Richardson）

### 4.1 数据库表对应服务边界
**规则：** 微服务的核心分解原则是"一个服务拥有自己的数据库"。共享数据库是微服务反模式。服务间通信只能通过 API——不能直接读另一个服务的表。如果你发现两个服务操作同一张表，合并它们，或者重新划分边界。

### 4.2 Saga 模式处理跨服务事务
**规则：** 不要用分布式事务（XA/2PC）。用 Saga——一系列本地事务 + 补偿操作（回滚）。设计 Saga 时务必要考虑：每一步失败时，向上一步发什么补偿命令？补偿本身可能失败怎么办？

### 4.3 CQRS：分离命令与查询
**规则：** 当读写负载不对称（大量读 vs 少量写，或复杂的查询需求）时，将写模型和读模型分离为不同的数据结构和接口。命令侧用领域模型，查询侧用物化视图/读模型。不要强迫一个模型同时满足两者。

### 4.4 服务发现 + 断路器 + 重试退避
**规则：** 在分布式环境中，网络会失败、服务会变慢。每个服务间调用必须封装：断路器（防止级联故障）、超时（不能无限等待）、重试带指数退避（不把压力堆回去）、和熔断降级的默认值。

### 4.5 API 网关是系统的前门
**规则：** 客户端不应直接与多个微服务通信。使用 API 网关作为唯一的入口点，负责路由、认证、限流、协议转换。网关不要包含业务逻辑——它只是一个中间层。

## 五、Martin Fowler 架构思想（Microservices / Refactoring / Patterns）

### 5.1 可进化的架构：先做对，再做快
**规则：** 不要为不确定的未来过度设计。设计架构使其容易改变，而不是预测所有变化。先做最简可用实现，通过持续重构（refactoring）演化。如果一个架构让你不敢改代码，那就是过度设计。

### 5.2 微服务的本质是独立部署
**规则：** 服务如果没有独立部署的能力，就不是微服务，只是分布式单体。判断标准：你能只改这一个服务、只部署这一个服务、而不影响其他服务吗？如果不能，先解决部署耦合。

### 5.3 持续集成 + 持续交付是架构的基础设施
**规则：** 没有 CI/CD，微服务架构无法运作。自动化测试、自动化构建、自动化部署是保证独立服务不互相破坏的唯一方法。如果团队没有成熟的 CI/CD 管道，不要拆微服务。

### 5.4 用模式命名沟通
**规则：** 团队交流时使用设计模式名称（Strategy、Observer、Saga、Event Sourcing）作为精确定义的术语。这消除二义性——"用 Observer 模式"比"一个东西变了另一个东西要知道"精确得多。

### 5.5 数据一致性边界：最终一致性是可接受的
**规则：** 不是所有操作都需要强一致性。在分布式系统中，识别哪些操作可以接受最终一致性，哪些必须强一致。强一致的范围越小，系统可扩展性越高。

## 六、整洁架构（Clean Architecture — Robert C. Martin / Uncle Bob）

### 6.1 依赖规则：依赖只能从外向内
**规则：** 源代码依赖必须只指向内层。外层（框架、数据库、UI）可以依赖内层（用例、实体），但内层绝对不能知道外层的任何东西。实体层不 import 任何框架代码。这是整个架构的核心——违反这个规则就是架构腐败的开始。

### 6.2 业务逻辑独立于框架
**规则：** 业务规则和用例应该是纯的——它们不应该继承框架的类、不应该调用 ORM、不应该引用 HTTP 请求对象。框架是工具，不是架构的根基。如果你发现业务代码里 import 了 Django/Spring/Express，说明依赖规则被打破了。

### 6.3 用例是系统的中心
**规则：** 每个功能需求对应一个用例（Use Case）。用例描述"系统接收什么输入，执行什么业务规则，产生什么输出"。先把用例写清楚，再考虑用什么框架、数据库、UI。用例是架构的中心，数据库是细节。

### 6.4 边界用接口隔离
**规则：** 架构边界两侧的通信通过接口（接口适配器）进行。外层为内层实现接口，内层定义接口。当数据库从 PostgreSQL 换成 MongoDB 或从 REST 换成 GraphQL 时，只改外层——用例代码一行都不动。

### 6.5 细节可替换性
**规则：** 数据库、Web 框架、文件系统、外部 API——这些都是"细节"，是可替换的实现细节。架构的目标是让这些细节的替换代价最小化。写代码时经常问自己："如果我要换数据库，要改多少文件？"答案应该是"只有 Gateway 层的文件"。

## 七、分布式系统（MIT 6.824 — Spring 2020 / 6.5840）

### 7.1 构建可容错的系统：假设一切会失败
**规则：** 设计分布式系统的基础假设：任何机器随时可能崩溃、网络可能分区、消息可能丢失或延迟。代码必须假设这些失败会发生，并且在失败时系统仍然正确（安全性和活跃性）。先写错误处理代码，再写正常路径。

### 7.2 RPC 语义：至少一次 vs 至多一次 vs 恰好一次
**规则：** 每次 RPC 调用都必须在三种语义之间选择。默认使用至少一次（at-least-once）+ 幂等处理组合来实现实际的恰好一次效果（exactly-once）。如果调用不是幂等的，需要去重机制（请求 ID + 去重表）。

### 7.3 共识算法（Raft/Paxos）是实现一致性的基石
**规则：** 当多个副本需要就某个值达成一致时（如谁是 leader、日志如何复制），必须使用共识算法（Raft、Paxos）。不要自己发明共识协议——99% 的情况下你会搞错。使用经过验证的实现（etcd/Raft、ZooKeeper/Zab）。

### 7.4 强一致性有性能代价
**规则：** 线性一致性（linearizability）是最强的保证，它使系统行为像单机一样，但代价是吞吐量下降和延迟增加。在选型时优先考虑较弱的一致性模型（因果一致性、最终一致性），仅在业务必须时（如银行转账、唯一 ID 生成）才使用强一致。

### 7.5 MapReduce 思想：分而治之 + 数据局部性
**规则：** 处理大规模数据的基本范式：将计算推到数据所在的位置（数据局部性），而不是把数据拉到计算节点。Map 阶段并行处理数据分片，Reduce 阶段聚合结果。这个模式适用于一切大数据/并行任务——先分区、再处理、再聚合。

## 八、并发模式（Concurrency Patterns — Go/Java/Actor Model）

### 8.1 不要通过共享内存通信，要通过通信共享内存
**规则：** 使用并发原语（channel、actor mailbox、消息队列）来同步数据访问，而不是依赖共享内存 + 锁。消息传递消除了竞态条件和死锁类问题。如果必须用锁，将其封装在最小范围内，并用高级同步原语（如读写锁、StampedLock）而非裸 mutex。

### 8.2 控制 goroutine/线程的生命周期
**规则：** 所有创建的并发单元（goroutine、线程、actor）都必须有明确的退出条件。使用信号（context.Done()、cancellation token、stop channel）来优雅关闭。创建 goroutine 的代码有责任确保它能被停止。孤儿 goroutine 是资源泄漏的根源。

### 8.3 扇出/扇入管道模式
**规则：** 使用生产者-消费者管道分解并发处理流程：一个阶段的输出是下一阶段的输入。扇出（fan-out）分发任务到多个 worker 并行处理，扇入（fan-in）收集结果到单一通道。每个管道阶段只做一件事，通过 channel 类型定义清晰的接口。

### 8.4 避免竞态：用原子操作和不变性（immutability）
**规则：** 共享可变状态是并发 bug 的第一来源。优先使用不可变数据结构（immutable data），其次是原子变量（atomic），最后才是锁。在 actor 模型中，每个 actor 的状态是私有的，只能通过消息修改——这是模仿这种模式的最佳实践。

### 8.5 并发不是并行
**规则：** 并发（concurrency）是代码结构——你将独立执行的任务解耦；并行（parallelism）是运行时——这些任务同时执行。先通过并发分解写出正确的程序，再考虑并行优化。不要为没有足够 CPU 核心的系统做过度并行化。

## 九、API 设计（RESTful & RPC & GraphQL Design）

### 9.1 一致的命名和资源建模
**规则：** API 中的资源名称使用名词复数（/users、/orders），操作通过 HTTP 方法表达（GET=读、POST=创建、PUT=全量替换、PATCH=部分更新、DELETE=删除）。保持 URL 路径层级一致，不使用动词在路径中。如果你发现 /createUser 这样的路径，那是反 REST 的。

### 9.2 状态无关（Stateless）设计
**规则：** API 请求必须携带所有需要的信息，服务器不保存客户端会话状态。认证信息通过 token/header 传递，分页信息通过 query 参数传递。无状态性让 API 可以水平扩展——任何请求可以被任何实例处理。

### 9.3 版本控制是契约
**规则：** API 从第一天起就带版本号（/v1/users）。规则：向后兼容的修改（添加字段）不需要新版本；不兼容的修改（删除/重命名字段、改变行为）必须升版本。永远不要修改已发布 API 的语义来"适配"新的需求。

### 9.4 错误响应标准化
**规则：** 所有 API 错误响应使用统一结构：`{"error": {"code": "ORDER_NOT_FOUND", "message": "Order with id 123 not found", "details": {...}}}`。HTTP 状态码用于大类（4xx=客户端问题，5xx=服务端问题），error code 用于程序化处理。错误信息要可读、可操作、不泄露内部实现细节。

### 9.5 安全默认：认证 + 限流 + 输入校验
**规则：** 每个 API 端点默认需要认证（除非显式标记为 public）。实施速率限制（rate limiting）防止滥用。所有输入在进入业务逻辑前必须经过校验和清洗——不要信任任何来自客户端的数据。对敏感操作实施幂等性保障（idempotency key）。
