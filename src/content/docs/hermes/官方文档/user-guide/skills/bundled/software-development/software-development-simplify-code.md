# 简化代码 —— 并行审查与清理

使用三位专注的审查者并行审查你的近期代码变更，汇总他们的发现，并应用值得修复的更改。

**核心原则：** 三位窄范围审查者胜过一位宽范围审查者。每位审查者深入搜索代码库，只关注一类问题 —— 复用、质量、效率 —— 而不会将注意力分散到所有三类上。它们并发运行，因此你只需要承担一次审查的延迟，而不是三次。

## 何时使用

当用户说出以下任何内容时触发此技能：

- "simplify" / "simplify my changes" / "simplify these changes"
- "review my code" / "review my recent changes" / "clean up my changes"
- "/simplify"（如果他们沿用了 Claude Code 的习惯）

用户可能添加的可选修饰符 —— 请尊重它们：

- **焦点（Focus）：** "simplify focus on efficiency" → 仅运行效率审查者（或向该方向加权聚合）。认可的焦点：`reuse`, `quality`, `efficiency`。
- **试运行（Dry run）：** "simplify but don't change anything" / "just report" → 运行三位审查者，呈现发现，不应用任何更改。在应用前询问。
- **范围（Scope）：** "simplify the last commit" / "simplify staged" / "simplify src/foo.py" → 相应缩小差异来源（参见第一阶段）。

不要在每次编辑后自动运行此技能。它消耗相当于三个子代理的 Token —— 仅在用户明确要求时调用。

## 流程

### 第一阶段 —— 识别变更

捕获要审查的差异。根据用户要求选择来源，默认顺序如下：

```bash
# 1. 默认：工作树中未提交的变更（已跟踪文件）
git diff

# 2. 如果为空，则包含暂存的变更
git diff HEAD

# 3. 用户可能请求的范围变体：
git diff --staged                 # "暂存的变更"
git diff HEAD~1                    # "上一次提交"
git diff main...HEAD              # "当前分支" / "我的 PR"
git diff -- src/foo.py            # 指定文件
```

如果 `git diff` 和 `git diff HEAD` 均为空，且不存在 Git 仓库或没有变更，则回退到用户明确命名的文件或在此会话中最近创建/编辑的文件。如果你确实找不到任何变更的代码，请告知用户并停止 —— 没什么可简化的。

捕获完整的差异文本。注意其大小：如果非常大（例如超过 2000 行变更），则警告用户三个子代理各自携带完整差异将消耗大量 Token，并建议在继续之前缩小范围（按目录、按提交）。

### 第二阶段 —— 并行启动三位审查者

使用 `delegate_task` **批处理模式** —— 在单个 `tasks` 数组中传递所有三个任务，使它们并发运行。这种模式三个任务正好，在任何默认安装的 `delegation.max_concurrent_children` 预算范围内。

给**每位**审查者提供**完整的差异**（而不是片段 —— 跨文件问题隐藏在间隙中），以及仓库的绝对路径，以便它们能够搜索更广泛的代码库。每位审查者获得 `terminal`, `file`, 和 `search` 工具集（以便它们可以执行 `git`, `read_file`, 和 `search_files`/grep）。

告诉每位审查者：
- 在现有代码库中搜索证据（不要仅凭差异推理）。
- **应用 Chesterton 栅栏（Chesterton's Fence）：** 在标记任何内容以删除之前，对该行执行 `git blame` 以理解其存在的原因。如果你无法确定原始目的，则标记为 `confidence: low` —— 不要猜测。
- 以结构化方式报告发现，包含信心和风险：
  ```
  文件:行号 → 问题 → 建议修复 | confidence: high/medium/low | risk: SAFE/CAREFUL/RISKY
  ```
  - **SAFE** = 证明不影响行为（未使用的导入、注释掉的代码、透传封装器）。自动应用这些。
  - **CAREFUL** = 在不改变语义的情况下改进（重命名局部变量、展平嵌套三元、提取辅助函数）。在测试验证后应用。
  - **RISKY** = 可能改变行为或破坏公共契约（N+1 重构、公共 API 重命名、内存生命周期变更）。标记为需要人工审查 —— 不要自动应用。
- 跳过琐碎问题及纯样式变更。仅标记能够实质性改进代码的内容。

传递这三个目标（如果用户焦点排除了某个，则丢弃）：

**审查者 1 —— 代码复用**
> 审查此差异中是否有重复代码库中已有功能的代码。搜索工具模块、共享帮助程序和相邻文件（使用 search_files / grep）查找新代码可以调用而非重新实现的现有函数、常量或模式。标记：重复现有函数的新函数；现有工具已经实现的手写逻辑（手动字符串/路径操作、自定义环境检查、临时类型守卫、重新实现的解析）。对于每个，指明要使用的现有内容及其位置。

**审查者 2 —— 代码质量**
> 审查此差异中的质量问题。查找：冗余状态（重复或可从现有状态推导出的值；不需要存在的缓存）；参数膨胀（新参数附加在应重构的函数上）；复制-粘贴-变体（应共享抽象的近重复块）；抽象泄漏（暴露内部细节，破坏现有封装边界）；字符串化代码（原始字符串，其中常量/枚举/注册表已存在 —— 在标记前检查规范注册表）；AI 生成垃圾模式（重申明显代码的额外注释，如 `count++` 上方的 `// increment counter`；对已验证输入的不必要防御性空检查；绕过类型系统的 `as any` 转换；与文件其余部分不一致的模式）。对每个给出具体重构建议。

**审查者 3 —— 效率**
> 审查此差异中的效率问题。查找：不必要的工作（冗余计算、重复文件读取、重复 API 调用、N+1 访问模式）；遗漏的并发（独立操作顺序执行）；热路径膨胀（启动或每次请求路径上的繁重/阻塞工作）；TOCTOU 反模式（在执行操作前而不是直接操作并处理错误时进行存在性预检查）；内存问题（无界增长、缺少清理、监听器/句柄泄漏）；过于宽泛的读取（当切片即可时加载整个文件）；静默失败（空 catch 块、忽略的错误返回、`except: pass`、`.catch(() => {})` 且无处理、错误传播缺口 —— 这些隐藏了 bug，至少应在吞掉之前记录日志）。对每个给出具体修复和原因。

### 第三阶段 —— 汇总并应用

等待所有三位返回（批处理模式一起返回）。

1. **合并**发现结果为一个列表，去除审查者重叠的重复项。
2. **丢弃误报** —— 你拥有最多的上下文；你不必与审查者争论，只需默默丢弃弱或错误的建议。
3. **解决冲突。** 审查者可能意见不一（审查者 1："使用现有工具 X"；审查者 3："X 很慢，内联它"）。默认解决顺序：**正确性 > 用户明确的焦点 > 可读性/复用 > 微性能。** 除非路径确实很热，否则不要应用损害清晰度的性能“修复”。当两个建议互斥且均合理时，选择改动代码较少的那个，并注明替代方案。
4. **按风险层级顺序应用：**
   - **首先 SAFE**（自动应用）：未使用的导入、注释掉的代码、透传封装器、冗余类型断言。之后运行测试。
   - **其次 CAREFUL**（验证后应用，一次一个文件）：重命名局部变量、展平三元、提取帮助程序、合并重复项。每个文件后运行测试。回滚任何破坏的更改。
   - **最后 RISKY**（标记为人工审查 —— 不要自动应用）：N+1 重构、公共 API 更改、并发修复、错误处理更改。每个都附带风险描述和测试覆盖状态呈现。
   - 如果用户选择了试运行，则呈现所有三个层级，不应用任何更改。
5. **验证**未破坏任何内容：运行受影响文件的针对性测试（而非完整测试套件），并重新运行仓库使用的任何 linter/类型检查。如果修复破坏测试，则回滚该修复并报告。
6. **总结**你更改了什么：按审查者类别和风险层级分组的已应用修复的简短列表，以及你故意跳过的任何发现及其原因。

## 陷阱

- **不要分散到超过 3 个。** 更多审查者意味着更多成本和更多需要协调的冲突建议，而非更好的覆盖。三个类别可覆盖空间。
- **给每位审查者完整的差异。** 将差异分散在审查者之间违背设计 —— 跨文件重复和 N+1 只有在看到全貌时才会显现。
- **审查者需要搜索，而非猜测。** 一个没有指向现有工具（“可能有一个帮助程序”）的复用发现是噪音。要求提供 `file:line` 证据；丢弃缺乏证据的发现。
- **应用 ≠ 重写。** 这是对用户近期变更的清理，而不是对整个模块进行重构的许可。将编辑范围限定在差异触及的内容以及修复所需的最小周边更改。
- **尊重项目惯例。** 如果仓库有 AGENTS.md / CLAUDE.md / HERMES.md 或 linter 配置，将这些规则纳入审查者提示中，以便建议匹配内部风格而不是与之冲突。
- **大型差异会耗尽上下文。** 如果差异巨大，请在委托前缩小范围 —— 三个子代理各自携带 5000 行差异成本高昂且可能截断。
- **过度信任死代码工具。** `knip`, `ts-prune`, 和 `depcheck` 标记实际上是动态使用的导出（字符串式导入、反射）。在删除之前始终 grep 搜索符号名 —— 工具报告干净不是证据。
- **未检查公共契约即重命名。** 导出名称、API 路由路径、数据库列名和配置键都是契约 —— 即使名称不好，重命名也会破坏消费者。将公共契约更改标记为 RISKY；永远不要自动重命名它们。
- **移除“不必要的”错误处理。** 空的 catch 块或忽略的错误可能是故意的 —— 在该上下文中错误是预期且无害的。标记它，不要移除它；让人工决定。
