## 阶段 4：实施（Implementation）

**修复根本原因，而非表面症状：**

### 1. 创建失败测试用例

- 最简单的可复现方法
- 尽可能自动化测试
- **必须在修复前完成**
- 使用 `test-driven-development` 技能

### 2. 实施单一修复

- 针对已识别的根本原因
- **一次只做一个更改**
- 不要进行“顺手”的改进
- 不要捆绑重构

### 3. 验证修复

```bash
# 运行特定的回归测试
pytest tests/test_module.py::test_regression -v

# 运行完整测试套件——确保无回归
pytest tests/ -q
```

### 4. 如果修复无效——三次原则（Rule of Three）

- **立即停止。**
- 计数：你尝试了几次修复？
- 如果 &lt; 3：回到阶段 1，根据新信息重新分析
- **如果 ≥ 3：立即停止并质疑架构（见下方步骤 5）**
- **在没有讨论架构之前，不要尝试第 4 次修复**

### 5. 如果 3 次以上修复失败：质疑架构

**表明存在架构问题的模式：**
- 每次修复都会在不同地方发现新的共享状态/耦合
- 修复需要“大规模重构”才能实施
- 每次修复都会在其他地方产生新的症状

**停止并质疑基础问题：**
- 这个模式从根本上讲是否合理？
- 我们是否“纯粹因为惯性而坚持它”？
- 我们是否应该重构架构，而不是继续修补症状？

**在尝试更多修复之前与用户讨论。**

这不是一个失败的假设——这是一个错误的架构。

## 危险信号——立即停止并遵循流程

如果你发现自己有这样的想法：
- “先快速修复，以后再来调查”
- “就改一下 X 试试看行不行”
- “做多个修改，然后跑测试”
- “跳过测试，我手动验证”
- “可能是 X 的问题，让我修复它”
- “我还没有完全理解，但这可能管用”
- “模式说是 X，但我换个方式来适配”
- “主要问题是：[列出修复列表，但未经过调查]”
- 在追踪数据流之前就提出解决方案
- **“再试一次修复”（已经尝试了 2 次以上）**
- **每次修复都在不同地方发现新问题**

**所有这些都意味着：立即停止。回到阶段 1。**

**如果 3 次以上修复失败：** 质疑架构（阶段 4 步骤 5）。

## 常见合理化借口

| 借口 | 现实 |
|------|--------|
| “问题很简单，不需要流程” | 简单问题也有根本原因。对于简单 bug，流程也能快速解决。 |
| “紧急情况，没时间走流程” | 系统性调试比猜试乱改更快。 |
| “先试这个，之后再来调查” | 第一次修复会设定模式。从一开始就做对。 |
| “等确认修复有效后再写测试” | 未经验证的修复不可靠。先写测试才能证明。 |
| “一次做多个修复节省时间” | 无法隔离哪些修改有效，还会引入新 bug。 |
| “参考文档太长，我改一下模式” | 部分理解必然导致 bug。完整阅读。 |
| “我看到问题了，让我修复” | 看到症状 ≠ 理解根本原因。 |
| “再试一次修复”（已失败 2 次以上） | 3 次以上失败 = 架构问题。质疑模式，不要继续修复。 |

## 快速参考

| 阶段 | 关键活动 | 成功标准 |
|-------|---------------|------------------|
| **1. 根本原因** | 阅读错误、复现、检查变更、收集证据、追踪数据流 | 理解“是什么”和“为什么” |
| **2. 模式** | 查找工作示例、比较、找出差异 | 知道差异在哪里 |
| **3. 假设** | 形成理论、最小化测试、一次一个变量 | 确认或提出新假设 |
| **4. 实施** | 创建回归测试、修复根本原因、验证 | Bug 解决，所有测试通过 |

## Hermes Agent 集成

### 调查工具

在阶段 1 中使用这些 Hermes 工具：

- **`search_files`** — 搜索错误字符串、追踪函数调用、定位模式
- **`read_file`** — 读取带有行号的源代码，进行精确分析
- **`terminal`** — 运行测试、检查 git 历史、复现 bug
- **`web_search`/`web_extract`** — 查找错误消息、库文档

### 配合 delegate_task

对于复杂多组件调试，派发调查子代理：

```python
delegate_task(
    goal="调查为什么 [特定的测试/行为] 失败",
    context="""
    遵循系统化调试技能：
    1. 仔细阅读错误消息
    2. 复现问题
    3. 追踪数据流找到根本原因
    4. 报告发现——不要修复

    错误：[粘贴完整错误]
    文件：[失败代码的路径]
    测试命令：[确切的命令]
    """,
    toolsets=['terminal', 'file']
)
```

### 配合 test-driven-development

修复 bug 时：
1. 编写一个复现 bug 的测试（RED）
2. 系统化调试以找到根本原因
3. 修复根本原因（GREEN）
4. 测试证明修复有效并防止回归

## 实际影响

来自调试会议的经验：
- 系统化方法：15-30 分钟修复
- 随机修复方法：2-3 小时乱撞
- 首次修复成功率：95% 对比 40%
- 引入新 bug：几乎为零 对比 常见

**没有捷径。没有猜测。系统化总是胜出。**
