# 一三一规则

技术方案与权衡分析的结构化决策框架。当用户在多个方案之间做选择时（架构决策、工具选型、重构策略、迁移路径），此技能（Skill）会生成 1-3-1 格式：一个清晰的问题陈述、三个不同选项及其利弊、以及一个具体的建议，包含完成定义和实施计划。当用户要求"1-3-1"、说"给我一些选择"或需要在竞争方案间抉择时使用。

# 1-3-1 沟通规则

用于任务存在多个可行方案且用户需要明确建议时的结构化决策格式。生成简洁的问题框架、三个选项及其权衡、以及推荐路径的可行计划。

## 何时使用

- 用户明确要求 "1-3-1" 回复。
- 用户对技术决策说"给我一些选择"或"我有哪些选择"。
- 一个任务有多个可行方案，且存在有意义的权衡（架构、工具、迁移策略）。
- 用户需要一个可以提交给团队或利益相关者的提案。

**不要** 用于只有一个明显答案的简单问题、调试会话，或用户已经决定采用某个方案的任务。

## 流程

1. **问题**（一句话）
   - 用一句简洁的话陈述核心决策或期望结果。
   - 关注"是什么"，而不是"怎么做"——不包含实现细节、工具名或具体技术。
   - 保持紧凑。如果一句话里用了"和"，说明你在描述两个问题。

2. **选项**（正好三个）
   - 呈现三个不同且可行的方案，标记为 A、B、C。
   - 每个选项包含简要描述、优点（Pros）和缺点（Cons）。
   - 选项应代表真正不同的策略，而不是同一方法的细微变化。

3. **建议**（一个选项）
   - 根据用户的上下文和优先级，说明推荐哪个选项及其理由。
   - 直接陈述——这是你的专业判断，而非模糊说法。

4. **完成定义（Definition of Done）**
   - 列出推荐选项的具体成功标准。
   - 这些是具体、可验证的结果——而非模糊的期望。
   - 如果用户选择了其他选项，请修改此部分以匹配。

5. **实施计划（Implementation Plan）**
   - 执行推荐选项的具体步骤。
   - 在适用时包含具体命令、工具或操作。
   - 如果用户选择了其他选项，请修改此部分以匹配。

## 验证

- 回复中恰好有一个"问题"句子。
- 回复中恰好有三个选项（A、B、C），每个都有优缺点。
- 回复中有一个"建议"，选出一个选项并给出理由。
- 完成定义和实施计划与推荐的选项一致。
- 如果用户选择了不同选项，需相应更新建议、完成定义和实施计划。

## 示例

用户："针对我们的 API 客户端添加重试逻辑，给我一个 1-3-1。"

代理：

**问题：** 对外部服务的 API 调用在高负载下间歇性失败，需要优雅的重试处理。

**选项：**

- **选项 A：在共享工具中使用带抖动的指数退避。**
  优点：简单、广为人知的模式；所有调用方共享同一实现。
  缺点：无熔断机制；重试期间调用方仍会阻塞。

- **选项 B：使用重试库（tenacity）作为每个端点调用的装饰器。**
  优点：每个端点可配置；内置支持熔断器和速率限制。
  缺点：增加依赖；装饰器模式可能模糊控制流。

- **选项 C：基于队列的异步重试，带有死信处理。**
  优点：非阻塞；失败调用可追踪并可重放；扩展性好。
  缺点：复杂度显著增加；需要队列后端；对于低流量服务过于复杂。

**建议：** 选项 A。调用量不足以证明队列基础设施的合理性，而带抖动和指数退避的共享工具能干净地处理故障模式，且无需新增依赖。

**完成定义：**
- `api_retry()` 工具处理临时 HTTP 错误（429, 502, 503, 504）。
- 最多重试 3 次，使用指数退避和抖动。
- 所有外部 API 调用都通过重试工具路由。
- 每次重试尝试都记录端点和尝试次数。
- 测试覆盖重试耗尽、立即成功以及临时故障后成功等场景。

**实施计划：**
1. 创建 `utils/api_retry.py`，包含可配置的最大重试次数、基础延迟和可重试状态码。
2. 使用 `random.uniform(0, base_delay)` 添加抖动以防止惊群效应。
3. 在 `api_client.py` 中使用重试工具包装现有 API 调用。
4. 添加单元测试，模拟每种重试场景的 HTTP 响应。
5. 通过对一个不稳定的端点模拟进行简单的压力测试来验证负载下的行为。
