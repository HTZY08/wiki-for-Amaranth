# 对抗性用户体验测试（Adversarial UX Test）

扮演产品的最差用户——那个讨厌技术、不想用你的软件、并且会找到各种理由抱怨的人。然后通过实用主义过滤器筛选他们的反馈，将真实的用户体验问题与“我讨厌电脑”的噪音区分开来。

把它想象成一个自动化的“妈妈测试”——但是脾气暴躁的版本。

## 为什么有效

大多数质量保证（QA）发现的是缺陷（bugs）。这个发现的是**摩擦（friction）**。一个技术上正确的应用对真实用户来说可能仍然无法使用。对抗性角色（adversarial persona）能够捕捉到：
- 对开发者有意义但对用户来说令人困惑的术语
- 完成基本任务需要太多的步骤
- 缺少引导或“顿悟时刻（aha moments）”
- 可访问性问题（字体大小、对比度、点击目标）
- 冷启动问题（空状态、没有演示内容）
- 阻碍转化的付费墙/注册摩擦

**实用主义过滤器（pragmatism filter）**（第三阶段）是让这个工具变得有用而非仅仅有趣的关键。没有它，你可能会在每个屏幕上添加一个“打印此页”按钮，因为爷爷不会弄 PDF。

## 如何使用

告诉代理（agent）：
```
"对我应用的 [URL] 运行一次对抗性用户体验测试"
"扮演一个暴躁的 [角色类型] 并测试 [应用名称]"
"在我的预发布站点上做一个混蛋用户测试"
```

你可以提供一个角色（persona），或让代理基于你产品的目标受众生成一个。

## 第一步：定义角色（Persona）

如果没有提供角色，通过回答以下问题生成一个：

1. **对这个产品来说，最难的（HARDEST）用户是谁？**（50岁以上，非技术角色，几十年用“老方法”做事的经验）
2. **他们的技术舒适度如何？**（越低越好——只使用 WhatsApp、纸质笔记本、老婆帮他们设置邮箱）
3. **他们需要完成的**一件事**是什么？**（他们的核心工作，不是你的功能列表）
4. **什么会让他们放弃？**（太多点击、术语、慢、令人困惑）
5. **他们沮丧时怎么说话？**（直率、粗鲁、不屑、叹气）

### 好的角色示例
> **“大麦克”麦卡利斯特**——58岁的体能教练。只用 WhatsApp 和纸笔。他的“电子表格”是一本纸质笔记本。“如果10秒内搞不定，我就回去用笔记本。”需要记录25名球员的训练结果。讨厌小字、术语和密码。

### 糟糕的角色示例
> “一个不喜欢这个应用的用户”——太模糊，没有约束，没有语气。

角色必须**足够具体**，以便在20分钟的测试中保持角色状态。

## 第二步：成为混蛋（以角色身份浏览）

1. 阅读任何可用的项目文档以了解应用上下文和网址
2. **完全代入角色**——他们的沮丧、限制、目标
3. 使用浏览器工具导航到应用
4. **尝试角色的实际任务（ACTUAL TASKS）**（不是功能导览）：
   - 他们能做到他们想做的事吗？
   - 需要多少次点击/多少个画面才能完成？
   - 什么让他们困惑？
   - 什么让他们生气？
   - 他们在哪里迷失？
   - 什么会让他们放弃并回到老方法？
5. 测试以下摩擦类别：
   - **第一印象**——他们是否会进入应用页面？
   - **核心工作流**——他们最常需要做的**一件事**
   - **错误恢复**——当他们做错事时会发生什么？
   - **可读性**——文字大小、对比度、信息密度
   - **速度**——感觉比他们当前的方法快吗？
   - **术语**——是否有他们不理解的术语？
   - **导航**——他们能找到回去的路吗？知道自己在哪吗？
6. 对每个痛点截图
7. 检查每页的浏览器控制台是否有 JS 错误

## 第三步：吐槽（以角色身份写反馈）

**以角色的身份**写反馈——用他们的语气，他们的沮丧。这不是缺陷报告。这是一个真实的人在发泄。

```
[角色名称] 对 [产品] 的评价

总体评价：[他们会继续使用吗？是/否/有条件的也许]

好的方面（勉强承认）：
- [连他们都不得不承认好用的东西]

坏的方面（合理的用户体验问题）：
- [会阻止他们使用产品的真正问题]

丑陋的方面（致命问题）：
- [会让他们立即卸载/取消的东西]

具体投诉：
1. [页面/功能]：“[用角色语气引述]”——[发生了什么，预期什么]
2. ...

结论：“[一句话总结他们体验的角色引述]”
```

## 第四步：实用主义过滤器（关键——不可跳过）

**脱离**角色。以产品人员的方式评估每个投诉：

- **红色：真实的用户体验缺陷（REAL UX BUG）**——任何用户都会遇到这个问题，不只是脾气坏的用户。修复它。
- **黄色：有效但低优先级（VALID BUT LOW PRIORITY）**——真实问题但只对极端用户有影响。记下来。
- **白色：角色噪音（PERSONA NOISE）**——是“我讨厌电脑”在说话，不是产品问题。跳过。
- **绿色：功能请求（FEATURE REQUEST）**——投诉中隐藏的好想法。考虑它。

### 过滤标准
1. 一个35岁、能干但忙碌的用户会有同样的抱怨吗？→ 红色
2. 这是一个真正的可访问性问题（字体大小、对比度、点击目标）吗？→ 红色
3. 这是“我希望它像纸一样工作”这种对数字化的抵制吗？→ 白色
4. 这是角色偶然遇到的真正工作流低效问题吗？→ 黄色或红色
5. 修复这个问题会给80%的正常用户增加复杂性吗？→ 白色
6. 这个投诉是否揭示了一个缺失的引导时刻？→ 绿色

**此过滤器是强制性的（MANDATORY）。** 永远不要把原汁原味的角色投诉直接做成工单。

## 第五步：创建工单（Tickets）

仅针对**红色**和**绿色**项目：
- 清晰、可操作的标题
- 包含角色的原话引用（有趣且令人难忘）
- 背后真实的用户体验问题（客观）
- 建议的修复方法（可操作）
- 标签/标记："ux-review"

对于**黄色**项目：创建一个包含所有备注的汇总工单。

**白色**项目仅出现在报告中。不创建工单。

**每次会话最多10个工单**——聚焦在最差的问题上。

## 第六步：报告

交付：
1. 角色的吐槽（第三步）——有趣且有代入感
2. 过滤后的评估（第四步）——务实且可操作
3. 创建的工单（第五步）——附带链接
4. 关键问题的截图

## 提示

- **每次会话只用一个角色。** 不要混合视角。
- **在第二、三步期间保持角色状态。** 仅在第四步时脱离角色。
- **先测试核心工作流。** 不要被设置页面分散注意力。
- **空状态是金矿。** 新用户体验最能揭示摩擦。
- **最好的发现是角色在尝试做其他事时意外撞上的红色项目。**
- **如果角色没有抱怨，说明你的角色太懂技术了。** 让他们更年长、更没耐心、更固执。
- **在演示、发布或推送一批功能后运行这个测试。**
- **尽可能以新用户身份注册。** 不要使用预填充的管理员账户——冷启动体验是摩擦最多的地方。
- **零个白色项目是一个信号，不是失败。** 如果实用主义过滤器没有发现噪音，说明你的产品有真实的用户体验问题，而不仅仅是一个暴躁的角色。
- **在测试之后检查项目文档中的已知问题。** 如果角色发现了一个已经在已知问题列表中的缺陷，这实际上是最具杀伤力的发现——意味着团队知道它，但从未感受过用户的痛苦。
- **订阅/付费墙测试至关重要。** 用过期账户测试，而不是只测活跃账户。“当你付不了钱时会发生什么”这种体验揭示了产品是否尊重用户，还是扣留用户数据。
- **计算完成角色一件任务所需的点击次数。** 如果超过5次，无论角色的技术水平如何，这几乎总是红色发现。

## 规则

- 在第二步和第三步期间保持角色状态
- 要真正刻薄但公平——找出真实问题，而不是制造问题
- 实用主义过滤器（第四步）是**强制性的**
- 每个投诉都需要截图
- 每次会话最多10个工单
- 在预发布/已部署的应用上测试，而非本地开发环境
- 一个角色，一次会话，一份报告
