# Gemini Decision 1 / Gemini Decisions API

**发布日期：** 2026-11-11
**来源：** https://blog.google/innovation-and-ai/technology/developers-tools/gemini-decisions-api
**工程范式：** 把"生成式模型"降维成"判别式打分器"——不做 token-by-token 解码，在候选选项上直接输出校准概率，用"零输出 token"把成本结构从按字计费改成按输入计费。

## 设计哲学

官方对痛点的描述是"bounded choices"：工具选择、策略检查、模型路由、上下文分级。这些都是闭集判断——答案在给定选项里，不需要写一段话。用生成模型做这类事，等于为了一个类别标签付一次完整解码的钱和延迟。

于是约束被还原成三条：单次前向、多问题共享一次输入、答案自带置信度。Gemini Decision 1 的定位是让"不确定的样本"能被自动分流到兜底或人工，而不是让模型去解释自己。

放弃的东西也很彻底：**它不产生任何文本**。不能解释理由，不能处理开放式问题，不能做需要组合新表述的任务。"表达力受限"是这类模型的固有代价，社区里对它最大的质疑正落在这里（下节）。另一个明确的放弃是通用性——它被绑定到一个新端点（Decisions API）和三种题型（yes/no、多选、有序打分），而不是复用 Interactions API。

## 关键架构决策

官方描述是"Built on Gemini's native multimodal architecture"，在候选集上打分而非解码。可核实的工程参数：

- **注意力/底座**：官方未披露底座来源、参数规模、上下文窗口的具体层数配置，只说基于 Gemini 的原生多模态架构。可核实的是可用上下文规格：共享输入最长 256K tokens。
- **输入组织**：一次请求 = 一个共享 `input`（`Content` block 格式，与 Interactions API 一致）+ 最多 1,000 个独立问题。每题只额外计自己的 instruction 与 criteria token；共享输入**只计费一次**，无论问多少题。图像/视频可调分辨率以换取视觉细节与 token 成本的平衡。
- **输出结构**：三种题型——`noul`（是/否，可带 true/false 描述判据）、`choice`（2–255 个选项，返回胜者与全部候选的归一化概率）、`score`（有序量规评分，从 0 起，返回连续加权分与各级概率）。每个答案附 0–1 的 confidence。
- **延迟特性**：模型计算中位数 50–100 ms，端到端 150–250 ms；关键的一条是"**从 1 题到 100 题几乎持平**"——因为解码被彻底去掉，问题数量不再是延迟的乘数。
- **成本结构**：$0.10 / 1M 输入 token，输出 token 计费为 0。官方称在自家共享基准套件上比 Gemini 3.5 Flash-Lite 走 Interactions API 便宜近 5 倍。没有输出 token 费、没有可变 thinking token 费、也不单独收音频转录和 OCR 的钱。
- **校准**：官方强调在该套件上"leads across the suite, with the lowest calibration error"。校准误差而不是准确率被摆到第一位，是因为下游代码要拿 confidence 做分流——这也是判别式模型最容易被误用的地方（见社区评价）。
- **训练/后训练策略**：原文未披露训练方法、reward 设计与数据构成。

## 关键结果

官方 blog 只给方向和单价，绝对分数在图表里。第三方（VentureBeat，2026-11-11）复述的 Google 发布数据如下，属**转述**，须按二手处理：

| 基准 | Gemini Decision 1 | GPT-6 Luna | Jev 1.14 |
| --- | --- | --- | --- |
| JevBench | 92.2% | 90.9% | 90.0% |
| Mind2Web Multimodal（浏览器任务） | 86.2% | — | 86.8% |
| When2Call（工具调用决策） | 79.9% | — | 82.0% |

- VentureBeat 称 Decision 1 在四个模型都跑的 7 项测试中领先 5 项，Jev 在 Mind2Web MM 与 When2Call 两项领先。
- 媒体类对比对象是 Gemini 3.5 Flash-Lite：MMAU（音频）71.8% vs 67.7%；Video-MME 69.1% vs 63.3%。

内部落地（官方自述，无第三方验证）：

- **Gemini Notebook 动态路由**：把请求实时分流到合适的模型档位与 thinking 级别，日常查询延迟最高降 40%，把重推理模型留给复杂任务。
- **Stitch 快速画布**：秒级生成产品流程的可交互线框，语音/点按的编辑几乎即时生效。
- **CC（Google Labs）表情选择**：从 200+ 选项里挑表情，避免引入额外延迟。
- **Google Search 的 MCP 工具安全层**：在延迟预算内检测对抗性行为与内容。

## 范式对比

- **vs GPT-6 系（OpenAI）**：OpenAI 的 Decisions API 在 10 月初进公测，比 Jev 晚约两周；Google 又晚约两个月。三家 API 形状高度相似（共享输入 + 打分 + 无输出 token），差别在模态覆盖与价格：Google 明确把"输入计费一次、千题共享"和"原生吃音频/视频/PDF"当作差异化。
- **vs Jev（TypeSafe）**：Jev 建立了这个品类的预期（9 月），在浏览器任务与工具调用决策两项上仍领先。Google 的胜点在多模态与校准，不在纯任务准确率。
- **vs 自家 Gemini 4 家族（Argon / Carbon / Hydrogen / Neon）**：那四档是在同一个生成式底座上做能力/成本分层；Decision 1 是换赛道——不参与 Intelligence Index 这类语言模型排行（Artificial Analysis 明确不排名决策模型），衡量单位从"分数"变成"每千次判断的成本"。
- **vs 传统小分类器**：这是社区里最锋利的对照（见下）——一个 Gemma 4 加向量嵌入的自建分类器，在具体任务上可能比通用决策模型好一倍，成本还更低。

## 社区评价

HN 讨论（`50456791`）集中批判三件事：

1. **品类原创性**：多个评论指出这个方向由 TypeSafe 的 Jev 在 9 月打开，OpenAI 两周后跟上、Google 两个月后才发；有人直接算时间差（"OpenAI 2 weeks after Jev, Google 2 months later"）。
2. **表达力与工程摩擦**：一线反馈称决策模型虽比 LLM 快得多，但"表达力有限"，把已有 LLM 后端重构成决策模型时摩擦很大，**已出现多个生产回滚的案例**；共识是"方向对，但模型层之上的工具链还差很多"。
3. **校准承诺的边界**：有人质疑"不要把一个未在我这类全新任务上校准过的模型卖成已校准"；另有实测称决策模型对 prompt injection 与诱导性提问的敏感度和底层模型一样，顺序（option order）依然影响结果。

另有一条对照实验（`50026075`）：同一项目上 Jev / OpenAI 等几家决策模型彼此只差几个百分点，改用传统 ML——Gemma 4 + 传统嵌入的小分类器——效果好一倍。这条批评指向该品类的真实护城河：**通用性本身就是它相对定制分类器的劣势**。

价格维度上也有分歧：有人认为比同赛道的决策模型贵，但"能直接吃音频和视频"这一条在特定场景值这个价。

## 可复用的工程经验

1. **闭集判断不要走解码路径**。工具选择、路由、合规检查这类任务，改成在候选上打分可把延迟从秒级压到百毫秒级，且问题数量近乎不影响延迟——这是本代最有普适性的结论。
2. **把"共享输入计费一次"当成架构约束来设计接口**。一请求多问题（1→1000）在成本上是指数级改善，前提是你的输入组织成一次共享上下文，而不是每个问题一份请求。
3. **先评估校准，再评估准确率**。下游要拿 confidence 做自动分流，校准误差大的模型会让"高置信度错误"直接穿透到生产；上线前必须按自己的任务分布重画可靠性曲线。
4. **选项顺序与措辞会污染结果**。既然仍是预测模型，option 排列和判据描述的措辞要当作超参处理，做顺序置换测试，别把它当确定性函数。
5. **先算自建分类器的基线**。如果你的任务窄、标注数据够，传统小模型 + 嵌入往往又快又准又便宜；通用决策模型的正当性来自"任务经常变、需要零样本"，不是来自绝对精度。
6. **把决策层当控制平面而不是能力层**。Google 自己的用法（路由、画布交互、表情、安全检测）都是"在延迟预算内做一次小判断"，而不是让它承担主任务。
