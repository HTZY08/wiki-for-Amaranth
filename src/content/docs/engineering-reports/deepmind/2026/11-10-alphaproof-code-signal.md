# Introducing AlphaProof Code: a breakthrough in verifying complex software at depth

**发布日期：** 2026-11-10
**作者：** Pushmeet Kohli、Swarat Chaudhuri（Google DeepMind）
**来源：** https://deepmind.google/blog/introducing-alphaproof-code/
**工程范式：** 不追求全自动形式化验证。把工作按人类研究团队的分工切开——人定"证什么"，agent 证"怎么证"，Lean 做机器检查，人只审 agent 标记出来的那 1%。这样做的收益不是省人，是把验证的**时间尺度**从"年"压到"周"。

## 设计哲学

约束是双层的，而且第二层才是这个项目真正的难点。

第一层是形式化验证本身：数学证明代码无缺陷，是安全保证的最高标准，但极其昂贵。历史做法是想办法缩小范围——只验协议设计，不验实现；只验关键片段，不验整条链。

第二层是**设计与实现之间的缝**。真实漏洞经常就藏在这里：协议规范是对的，编译出来的代码不对。所以只证设计层的性质，等于证明了"如果实现正确那么安全"，而现实中攻击者打的恰恰是"实现是否真的正确"。要把这条缝补上，就得证明编译后、跑在设备上的那份代码满足关键安全性质（例如"设备被临时攻破的前后，消息仍然受保护"）。这让证明复杂度上一个量级。

DeepMind 的选择因此不是"让 AI 写更多证明"，而是**重新划分人机边界**：

- 人 + 模型协作，把 Signal 的安全目标翻译成形式化数学规范，**每一条规范都有专家审核**；
- 由 agent（Gemini Carbon 驱动）去证；
- agent 自己审自己的证明，把需要人再看一遍的地方标出来——**只占代码库的约 1%**；
- 其余部分由 Lean 自动检查。

放弃的东西：放弃了"AI 独立决定证明目标"。规范是人审的，模型只负责把自然语言的安全目标转成形式化命题并完成证明。原文把这个边界写得很明确——"human experts work with AI to decide *what* to prove, and a group of AI agents does it"。这意味着系统无法自证它证的是"对的性质"，只能保证它证的性质成立。安全上这是必要的（否则模型可以挑一个好证的弱命题交差），工程上这也是它能在四周内落地的原因。

## 关键架构决策

- **整体形态**：multi-LLM agentic framework，多模型协作。不是单个模型端到端。
- **证明内核**：Lean。每一条证明都由 Lean 机器检查，这是唯一可信判分器——agent 无法自我认证。
- **模型分工**：规范翻译阶段使用"a mix of models"；证明阶段由 **Gemini Carbon** 驱动的 agent 完成。
- **对抗自检机制**：agent 在生成证明后再做一次审计，标出需要人复核的位置。这个环节把人工复核量从全量降到约 1%，是整条流水线的效率来源。
- **可信度验证（负样本测试）**：把两个真实存在、后来已被修复的 bug 重新注入隔离版 Signal 代码，两种情况下系统都产出了"机器检查通过的不安全性证明"。这是判断验证框架是否只是橡皮图章的关键实验。
- **注意力机制 / MoE 设计 / 训练策略 / 推理优化 / 后训练**：未披露。原文是研究成果公告，不含任何模型架构或训练细节。
- **与既有工具的衔接**：与 CodeMender 这类自动修复 agent 配对使用——先证，后修。

## 关键结果

- agent 生成 **超过 600 万行 Lean** 证明。
- 人工需要复核的范围：**约 1% 的代码库**。
- 端到端耗时：**四周**。原文对比称此类任务历史上需要专家团队数年。
- 覆盖范围：Signal 协议**编译后的代码**，而非仅设计层；原文称这是首次用 AI 对广泛部署的密码协议做到这个深度，也是首次有方法（无论是否用 AI）对这类广泛部署协议的实现完成形式化验证。
- 负样本验证：注入的两个真实 bug，**均**被证明为不安全。
- 产出开放：形式化验证工件（artifacts）开源，另附技术论文。

## 范式对比

- **对 Anthropic**：两家都在攻"AI + 安全"，但取的是不同证明方式。Anthropic 的路线是**评测与行为治理**——测模型会不会做坏事（Siren 测沙箱逃逸倾向）、给模型加分类器与监控；DeepMind 这条是**数学证明**——把"代码安全"变成机器可检查的定理，不依赖对模型的信任。前者管模型，后者管被模型产出的东西。两者互补，不互替。
- **对 OpenAI**：OpenAI 走的是"通才模型 + 代码执行"（见同日代的蛋白设计工作），判定标准是实验结果；DeepMind 这里判定标准是 Lean 内核，**不需要信任模型**。这是同一波"agent 做科学"里最重要的分野：靠实验判分 vs 靠形式系统判分，后者的可审计性高一个量级。
- **对传统形式化验证团队**：过去的可比成绩是 seL4 级别的微内核验证，规模在万行级、耗时数年。600 万行 Lean、四周，这个数量级差不是工程优化出来的，是把"人写证明"换成"人审 1% 证明"换出来的。
- **路线信号**：Google 把这件事和 CodeMender 并列，说明它的定位是防御侧基础设施——用自动定理证明对抗 agent 驱动的攻击速度。这是把 AI 安全从"对话层护栏"推到"代码层证明"的一次公开站位。

## 社区评价

加密与形式化验证圈的反应集中在两点。其一是规模：600 万行 Lean 对熟悉 Lean 生态的人来说是可以立刻判断量级的数字，四周内产出被认为是这条线上最硬的公开结果之一。其二是"1% 人工复核"到底意味着什么——批评者指出，剩下 99% 由 Lean 检查，但 **Lean 检查的是命题成立与否，不是命题是否描述了正确的安全目标**；系统正确性的根仍扎在人写的规范上。Signal CTO Ehren Kret 的公开表态（用 agent 把线上代码自动翻译成合法 Lean 定理是主要突破）被广泛引用，也被用来反问：这套方法的下一个瓶颈是规范撰写，不是证明生成。

## 可复用的工程经验

1. **给 agent 找一个它无法作弊的判分器**。Lean、类型检查器、单元测试、形式化 schema——凡是外部机制能一票否决的，都可以把 agent 产出从"看起来对"变成"确实对"。这是 agent 工程质量的第一道杠杆，比换模型有效。
2. **人工复核要按"需要判断的地方"分配，而不是按比例分配**。这里 agent 先自审再标出可疑点，人只看标记区。任何高产出流水线都该有这一步：让生成者先做筛选，再让审核者看筛剩下的。
3. **用真实历史 bug 做负样本测试**。想证明检查机制不是橡皮图章，最便宜的办法是把已知 bug 重新注入，看机制能不能抓到。低成本、高置信度，值得成为验证类系统的标准回归测试。
4. **把"证什么"和"怎么证"拆给不同的责任主体**。模型负责后者，人负责前者。这样即使模型能力继续涨，"它证错了对象"这个风险也不会随之涨。
5. **验证的对象要选实现，不要选设计**。只验设计的收益是有限的，因为漏洞常在设计与实现的缝里。代价是复杂度剧增——但这是唯一能对攻击者有效的口径。
6. **可审计产出要开源**。形式化 witness（工件 + 论文）开源后，第三方可以独立复核，这比任何自评指标都值钱。
