# GLM-5.4：Toward Generalized Coding with Our First Loop Transformer

**发布日期：** 2026-11-23
**来源：** https://z.ai/blog/glm-5.4
**工程范式：** 不再用参数量换推理深度——把已预训练的 GLM-5 底座中间 28 层反复跑两遍，用"计算深度"替代"参数规模"，配套重写 KV cache 与稀疏索引复用，让多跑一遍只多付一个滑动窗口的代价。

## 设计哲学

官方给的前提判断很明确：内存密集型任务吃参数，推理密集型任务吃有效算力。大规模软件工程、网络安全、3D 建模、物理控制属于后者——模型必须走完多步因果链并保持全局逻辑一致，"堆参数、背数据"解决不了。

于是他们把方向从"更大的模型"换成"更深的计算"。循环（looped）Transformer 不是新概念：2018 年的 Universal Transformer 就提出过权重共享深度，2026 年也有一批小规模循环语言模型的工作。但官方点出了一个关键的反面证据：**在同样的预训练算力预算下，从头训的循环模型仍然打不过非共享层模型**。这句话决定了他们整条路线——不从零训，而是把一个已经训好的底座"改装"成循环模型，用继续训练（continued training）把能力上限抬起来，代价只是"relatively small compute overhead"。

放弃的东西同样清楚：参数效率的收益换不来同算力下的对等性能，所以放弃了从零设计循环架构的自由；循环带来的额外前向计算直接变成延迟与配额成本，官方自己承认模型会陷入"marathon thinking"，**这正是社区抱怨最集中的地方**（见下文）。另外，权重没有随发布放出（"plan to open-source after completing necessary safety hardening"），API 也标注 Coming Soon，发布形态是产品先行、权重后置。

## 关键架构决策

- **循环方式**：GLM-5.4 把 GLM-5 底座的 **28 层循环两次**。这是"改装"而非"重训"的具体形态——不新增层，把中间一段层复跑一遍。
- **规模**：官方称 GLM-5.4 是"750B scale"，能力对标 2T–3T 参数模型（这是官方自述，未给第三方横评数字）。
- **门控渐进更新（Gated Progressive Updates）**：直接把中间层改多趟会出事——隐藏状态被覆盖后激活范数在迭代间爆炸，下游层收到超出预期尺度分布的表示。解法是给每一趟加独立的 per-token gate，按比例把候选更新写回残差流。训完后 gate 自己分化出分工：第一趟建立全局上下文、gate 值小、保守写入保持尺度稳定；第二趟复用该状态精修、gate 打开做完整写入。gate 还会按 token 难度动态调步长——难 token 第一趟写得更激进，让复杂预测更多受益于迭代。
- **混合 KV cache（全局共享 + 独立滑动窗口）**：朴素实现给每一趟循环都留一份完整 KV，显存随环数线性膨胀。他们的做法是在跨环 KV 共享之上，为新一轮补一个局部滑动窗口：第二趟复用第一趟选中的稀疏 KV，同时保留自己新生成的、落在滑动窗口内的 KV。两路 KV 可在同一位置重叠，模型既能看第一趟的上下文表示，也能看第二趟更新后的局部表示。结果是**多跑一环只多付一个滑动窗口的 KV，而非整段上下文 cache**——这是 1M 上下文下部署成本还能控住的关键。
- **稀疏注意力索引复用**：底座本身是稀疏注意力。第二趟直接复用第一趟 indexer 生成的注意力索引，索引开销为零。官方实测与每趟重算"nearly identically"。
- **正确性验证（Scaling Correctness）**：在把旗舰压上去之前，先在 1B / 4B / 30B / 750B 上逐级验证循环架构。在 30B（架构与 750B 底座完全一致）上做等参数对照：**参数完全相同、总训练算力只多约 10%**，循环版本取得明确增益（该 30B 对照在 200K 长上下文 SFT 后、开启 thinking 模式下评测）。两个发现：更长的推理链受益更大（数学、科学推理、长上下文涨幅最大）；**思考 token 更少**——GPQA-Diamond、MMLU-Pro 等基准上平均输出长度下降 10–14%，主要是思维链变短，即部分推理从显式输出 token 转移到循环的隐式深度里。
- **推理系统协同**：多趟循环放大了 kernel 之间中间显存读写碎片，他们在系统层融合核心 kernel 压掉这部分开销。吞吐官方数据：低谷时段最高 200 tokens/s，峰值负载维持 70–80 tokens/s。
- **后训练/数据**：原文未披露循环改造阶段的训练数据配比与 RL 细节，只说"继续训练 + 200K 长上下文 SFT"出现在 30B 对照里。

## 关键结果

**官方本次没有放出任何对比 benchmark 表。** blog 里的增益均以图表呈现、正文只给方向性表述（"largest gains show up in math, scientific reasoning, and long-context tasks"），30B 等参数对照的绝对数值也未在正文列出。这一点在发布当天就被社区点名（见下）。第三方观察（非官方）：DataCamp 的分析提到与 Gemini 4 Neon 相比存在约 15 倍 token 差、单任务耗时可达 30 分钟以上。

可核实的官方数字只有：

- 循环范围：GLM-5 base 的 28 层，两趟
- 规模：750B；宣称对标 2T–3T 参数级能力
- 等参数对照的算力增量：约 +10% 总训练算力（30B 模型）
- 思考长度变化：多数基准（GPQA-Diamond、MMLU-Pro 等）平均输出长度下降 10–14%
- 推理吞吐：off-peak 最高 200 tok/s，峰值 70–80 tok/s
- 验证规模阶梯：1B / 4B / 30B / 750B

## 范式对比

- **vs 自家 GLM-5.3**：5.3 是"底座冻结、只做后训练"，增益全来自环境工程；5.4 反过来动底座——同一个 GLM-5 base，但改造成循环结构。两代连续验证了同一个判断：能力瓶颈要么在环境侧、要么在计算深度侧，z.ai 两处都试了，都不靠加参数。
- **vs 同周的 Thinking Machines Inkling 2 Mini（11-20）**：两者都上循环 Transformer。Inkling 2 Mini 是"中间层跑三遍"换更少 token 的小模型路线；GLM-5.4 是拿成熟 750B 底座改装。循环正在从论文概念变成同一周内两家公司同时落地的工程选项——这是本次发布最值得记的信号。
- **vs Kimi K3.1 Pro / Qwen4-Max 这一批**：那两家仍在参数与 MoE 稀疏度上推进（2.8T/104B 激活、2.4T/71B 激活），z.ai 这次把筹码押在"同样参数跑更多算"上。真假要用每任务成本来判，而这恰好是官方没给数据的部分。
- **vs 闭源前沿（Fable 5.2 / GPT-6.2 Astra）**：z.ai 的卖点仍是开放权重 + 低价，但 5.4 的权重和 API 都还没到位，这一代的"开放"目前只是承诺。

## 社区评价

- r/LocalLLaMA 的讨论帖（`1y3enps`）最热的追问是"<30B 的那些验证模型在哪"——官方说在 1B/4B/30B/750B 上做了逐级验证，社区立刻要求把中间模型放出来，因为循环架构对小模型的意义可能比旗舰更大。其次是"会不会有 5.4 Flash"。
- 实际使用侧的核心抱怨是**思考太长**：首发实测出现单次运行 30–60 分钟、5 小时配额被快速烧穿、以及过载报错；有人描述一个 SVG 动画在动笔前先想了近 30 分钟。用户普遍把它归因于循环结构本身。
- 发布当天文档页报错、官方 benchmark 缺席，是"无数据发布"讨论的焦点。Simon Willison 的记录印证了两点：权重未开、只能通过 Coding Plan 订阅访问而非普通 API；同时他注意到这已是当周第二个循环 Transformer 发布。
- HN 提交（`50609685`）热度很低（提交时 7 分），说明这代在英文技术社区的存在感远低于 5.3。

## 可复用的工程经验

1. **先验证"等参数"，再动旗舰**。设一个与自己旗舰同架构的小模型（这里是 30B），保证参数完全相同、只差那个变量，算力增量控制在 10% 量级——这是判断"循环是否真的比更深更宽更好"的唯一干净实验。
2. **循环的显存账要按"多一环 = 一个滑动窗口"来设计**。跨环 KV 共享 + 局部滑动窗口重叠，是把多趟推理成本从"乘以环数"降到"加一个窗口"的关键；不做这一步，1M 上下文下的循环基本不可部署。
3. **改造中间层必须加 per-token gate**。直接覆盖隐藏状态会让激活范数跨迭代爆炸；让 gate 自己学出"第一趟保守、第二趟放开"的分工，比手工设衰减系数稳。
4. **索引能复用就复用**。稀疏注意力的第二趟沿用第一趟 indexer 输出，实测几乎无损，却省掉全部索引计算——这是低风险高收益的一类优化，值得在任何多趟结构里先试。
5. **循环模型要用"输出 token 数"而不是只看分数来验收**。官方最有说服力的数字是思考长度降 10–14% 而分数上升；反过来，如果分数涨但 token 涨得更多，在按 token 计费的场景里就是净亏。
6. **警惕"深思考"变成产品缺陷**。同一套机制在离线评测里是精度红利，在交互式产品里是延迟与配额灾难——上线前必须给思考长度设硬预算或自适应终止，否则社区反馈会直接否掉架构收益。
