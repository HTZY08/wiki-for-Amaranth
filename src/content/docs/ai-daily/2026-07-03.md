# 🔥 今日聚焦

## MiniMax Sparse Attention (MSA)：注意力机制的第三次范式转移

6月30日，MiniMax 发布 MiniMax Sparse Attention (MSA) 论文（arXiv 2606.13392），在 109B MoE 模型上，1M 上下文下实现 28.4x 注意力计算缩减，且质量零损失。这不是增量改进——这是继 MLA（压缩KV）和 DSA（块稀疏选择）之后，注意力机制的第三次范式转移。

MSA 的设计哲学可以概括为一句话：最小化额外开销，最大化 GPU 利用率。它的技术路线与 DeepSeek 的 DSA 和 GLM 的 IndexShare 形成了清晰的三种稀疏注意力路线对比。

MSA 的核心是双分支结构：一个极轻量的 Index Branch（只有两个投影矩阵）对 KV block 打分，每 GQA group 独立选择 top-k block；Main Branch 只对被选中的 block 做精确注意力计算。关键设计选择：block size = 128，k = 16（即每个 query 只看 2048 个 token 的 block），强制包含当前 query 所在 block 保证稳定性。Index Branch 的训练通过 KL 散度对齐实现，前 40B tokens 做 warmup 后再启用稀疏。

但 MSA 真正的工程量级不在算法，而在 GPU kernel 的协同设计。团队为 H800 写了三个定制 kernel：Exp-Free TopK 用 per-thread register min-heap 代替 softmax 排序阶段；KV-Outer Sparse Attention 把迭代顺序从 query-outer 翻转为 KV-outer，使算术强度从 G（query head 数）提升到 (2/3)*Bk（~85）；Sparse KL Loss Backward 用 persistent grid + global atomic counter 实现动态负载均衡。在 H800 上，128K 序列比 PyTorch 实现快 5.1x，512K 快 4.3x，1M 快 3.7x。

工程范式的关键洞察：MSA 没有追求理论最优的稀疏度，而是追求实际可部署的硬件速度。它选择 block-level 稀疏（而非 token-level）是因为 block 粒度能让 tensor core 用满；它选择每 GQA group 独立选择而非共享是因为 group-specific 稀疏能保留更多有效信息；它选择保留全部 KV cache（不压缩）是因为压缩 + 稀疏的组合复杂度太高，不如各司其职。

与竞品对比：DeepSeek DSA 走 token-level 细粒度选择路线，需要更复杂的 indexer；GLM IndexShare 走跨层共享 indexer 路线以降低计算量。三条路线各有取舍——MSA 最简洁，DSA 最精细，IndexShare 最节省 indexer 开销。但三者的共同趋势是明确无误的：2026年下半年的注意力标准将从「谁做 sparse attention」变成「谁做的 sparse attention 能真正跑出 wall-clock 加速」。

这里还有一个更大的信号：MSA 是 MiniMax M3 的基础架构。据社区推测，M3 将结合 MSA + 此前的 Forge RL 体系 + M2 的细粒度 MoE，形成完整的"注意力稀疏化 + 训练系统化 + 架构精细化"三线组合。如果推测成立，M3 可能成为第一家同时做好这三条线的公司。

## ByteDance Seed-Thinking-v1.5：双轨奖励系统解决 RL 的终极矛盾

ByteDance Seed 团队的 Seed-Thinking-v1.5 技术报告（arXiv 2606.xxx）展示了推理模型 RL 训练中一个被严重低估的工程问题——当你的任务既有可验证的数学题又有不可验证的创意生成时，单一奖励函数根本没法用。Seed-Thinking-v1.5 的答案是把奖励系统拆成双轨并行。

架构层面：200B 总参 / 20B 激活的 MoE，延续 Seed 系列的参数效率路线。训练分为 SFT + RL 两阶段，关键的创新在 RL 阶段的双轨奖励系统。可验证任务（数学、代码）走智能逻辑验证器（intelligent logic verification）——不是简单地检查答案对错，而是验证推理路径的每一步逻辑一致性。不可验证任务（创意写作、开放问答）走成对比较优化（pairwise comparison optimization）——用对比排序代替绝对打分。

这种设计的工程智慧在于：它承认了 RL 的核心矛盾——reward 信号越精确，覆盖的 task 类型越窄；覆盖越广，reward 信号越模糊。Seed 的做法不是找一个折中方案，而是把这两类任务从 reward 层面彻底解耦，各自用最适合的 reward 机制。代价是训练流程更复杂、需要两套 reward pipeline，但收益是数学推理和创意生成两类任务都不再互相拖累。

Seed-Thinking-v1.5 的 MoE 架构（200B/20B）延续了 Seed1.5-VL 的参数效率哲学：用更小的激活参数匹配更大规模的密集模型。在 AIME 2024 上 86.7，GPQA 上 77.3，Codeforces pass@8 上 55.0——与 DeepSeek R1（671B 总参/37B 激活）和 OpenAI o3-mini 相比，Seed 以约 1/10 的总参数量达到了可竞争水平。这是 ByteDance 工程路线的核心——不追最大，追最强效率比。

Source: seed.bytedance.com, github.com/ByteDance-Seed/Seed-Thinking-v1.5

# 📄 技术报告全景：工程范式分析

## MiniMax — MiniMax Sparse Attention (MSA, arXiv 2606.13392, Jun 2026)

链接：arxiv.org/abs/2606.13392

工程范式：硬核系统协同设计路线——不追求理论最优算法，追求在 H800 上能实际跑出 wall-clock 加速。

设计哲学：MiniMax 面对的核心约束是 ultra-long-context 推理的成本墙——1M token 的 full attention 在 109B 模型上根本不可部署。他们放弃了 token-level 细粒度稀疏（DSA 路线）而选择 block-level 粗粒度稀疏，因为 block 粒度能在 GPU tensor core 上跑满。关键决策：block-wise + GQA group-wise selection + 全量 KV cache 保留（不做压缩）。

关键架构决策：
- 注意力：双分支结构（Index Branch + Main Branch），block size 128，top-k = 16 blocks
- GPU kernel：三个定制 kernel（Exp-Free TopK, KV-Outer Sparse Attention, Sparse KL Loss Backward）
- 训练：前 40B tokens indexer warmup，之后启用稀疏；stop-gradient 设计防止 indexer 退化
- 推理：Prefill 在 1M 下 14.2x 加速，decode 7.6x 加速

范式对比：vs DeepSeek DSA（token-level 细粒度选择），MSA 更粗粒度但 wall-clock 更快。vs GLM IndexShare（跨层共享 indexer），MSA 每层独立 indexer 更灵活但计算量更大。

可复用的工程经验：如果要做 sparse attention，(1) 不要追求理论 FLOPs 缩减，要追求 wall-clock 加速；(2) block-level 优于 token-level，除非你不 care GPU 利用率；(3) indexer 的 warmup 是必须的，不 warmup 直接上 sparse 质量下降显著；(4) stop-gradient 防止 KL 蒸馏 collapse 是隐式但关键的 trick。

社区评价：r/LocalLLaMA 上讨论热烈："MSA 的 GPU kernel 设计值得每个做 attention 优化的团队学习。KV-Outer 迭代顺序的翻转是经典的系统优化思路——换个角度看问题，算术强度翻 30 倍。" r/MachineLearning 上有人指出 MSA 是 M3 的基础，市场反应正面。

## ByteDance Seed — Seed-Thinking-v1.5 (2026-Q2)

链接：seed.bytedance.com, github.com/ByteDance-Seed/Seed-Thinking-v1.5

工程范式：参数效率路线——用 1/10 的总参数量匹配更大模型的推理能力。

设计哲学：ByteDance 的核心约束是推理成本的商业可行性——亿万级用户的产品（豆包、抖音）不能跑成本巨大的模型。他们选择 MoE（200B/20B）而不是密集架构，因为激活参数少意味着推理成本低。关键 trade-off：总参数量大但激活少，意味着训练成本高但推理成本低，对面向消费者的公司是正确选择。

关键架构决策：
- MoE：200B 总参 / 20B 激活，延续 Seed1.5-VL 的设计
- RL 算法：双轨奖励——可验证任务走逻辑验证，不可验证走成对对比优化
- 数据系统：SFT 阶段的精确数据构造 + RL 阶段的算法创新
- 训练基础设施：未公开具体规模，但推测为大规模集群

范式对比：vs DeepSeek R1（671B/37B，统一 GRPO），Seed 的双轨奖励更定制化但更复杂。vs OpenAI o3（未公开架构但推测为密集），Seed 以 MoE 的低激活参数量打性价比。

可复用的工程经验：(1) 当 task 类型差异大时，别用统一 reward——拆成多轨奖励；(2) 逻辑验证器应该验证推理路径而非仅验证最终答案；(3) SFT 数据的构建质量比 RL 算法本身更重要。

社区评价：r/LocalLLaMA 上："Seed-Thinking-v1.5 是 20B 激活参数的推理模型，这个效率比足够让开源社区兴奋了。"

## Anthropic — Claude Fable 5 & Mythos 5 System Card (Jun 9-12, 2026)

链接：anthropic.com/news/claude-fable-5-mythos-5

工程范式：能力分层 + 安全防御工程路线——同一模型两种配置，用安全系统决定谁用什么能力。

设计哲学：Anthropic 面对的核心约束是能力快速增长与安全部署的矛盾。他们的答案是：不降能力，降访问权限。Fable 5 和 Mythos 5 是同一个底层模型，但 Fable 5 的安全分类器会在检测到高风险请求时自动降级到 Opus 4.8。关键放弃：Fable 5 在某些任务上用户得到的不是 Fable 5 的能力，而是 Opus 4.8 的。这建立在用户不会注意到降级、或者即使注意到也不会离开的假设上。

关键架构决策：
- 安全架构：双层分类器（probe + LLM classifier），覆盖 cyber/bio/chem/distillation 四个域
- 架构细节：底层模型细节未公开，已知支持 1M token 上下文、128K max output
- pricing：$10/$50 per M token（vs Opus 4.8 的 $4.8/$24）
- 自适应思考（adaptive thinking）：推理时动态调整思考深度

范式对比：vs OpenAI 的 GPT-5.5（统一模型，不做安全降级），Anthropic 的安全工程更激进。vs Google Gemini 3.5（走全面 agent 化路线），Anthropic 更聚焦纯安全工程。

社区评价：Reddit 上 "RIP Claude Fable 5 (June 9, 2026 – June 12, 2026)" 帖子生动记录了从发布到被美国政府叫停的全过程。Forbes 报道：美国政府引用 Anthropic 自身的安全报告来认证其风险等级。更大的问题是：这是单一冲突，还是前沿 AI 监管方式的预演？

## Google DeepMind — Gemini 3.5 Flash (Jun 24, 2026)

链接：blog.google/innovation-and-ai/models-and-research/gemini-models/gemini-3-5

工程范式：agentic 能力密度路线——把前沿智能压缩到最快的推理速度上。

设计哲学：Google 的核心约束不是能力不够，而是让能力被实际使用。Gemini 3.5 Flash 选择在中低推理成本上提供接近前沿的能力，核心新增是 Computer Use——让模型能直接操作屏幕、点击、输入。这个选择的信号意义：Google 认为 2026 下半年的竞争焦点已经从「谁能做最聪明的模型」转向「谁能让模型做最多的事」。

关键架构决策：
- 架构：具体细节未公开，Gemini 3.x 家族基于 MoE Transformer
- Computer Use：模型原生能力，非 RAG/外挂
- Agentic 能力：支持工具调用、屏幕操作、多步推理
- 多模态：延续 Gemini 家族的原生多模态设计

范式对比：vs Anthropic（专注安全降级），Google 专注 agentic 扩展。vs OpenAI（GPT-5.5 做统一模型），Google 做能力分层——Flash 做速度，Pro 做深度，Ultra 做极限。

可复用的经验：如果做 agentic 模型，(1) Computer Use 是下一个标配能力；(2) 推理速度 vs 能力深度是 2026 年最重要的 trade-off，没有之一。

## Moonshot — Kimi K2.7-Code (Jun 12, 2026)

链接：marktechpost.com/2026/06/12/moonshot-ai-releases-kimi-k2-7-code

工程范式：超大 MoE + Agent Swarm 路线——1T 参数模型配 300 个子 agent 的大规模协调架构。

设计哲学：Moonshot 的核心约束是长程编码任务的可靠性——单次对话需要数千步 agent 操作，任何一步出错都导致失败。他们相信用更多参数 + 更多子 agent 来解决这个问题：K2.7-Code 的 384 专家（8 活跃 + 1 shared）提供高质量的生成能力，Agent Swarm 系统的 300 个子 agent 提供执行广度。

关键架构决策：
- MoE：1T 总参，384 专家，8 active per token + 1 shared expert
- Agent Swarm：300 domain-specialized sub-agents，最高 4000 步连续执行
- 上下文：原生长上下文设计，优化 agent 轨迹的持续跟踪
- 发布：开放权重（Modified MIT），上线 GitHub Copilot

范式对比：vs DeepSeek V3.2（671B/37B，精简 MoE），Kimi 走超大 MoE 路线，参数量大但推理质量更高。vs Qwen3-Coder-Next（80B/3B，极致精简），Kimi 走另一极端——用大参数换可靠性。

社区评价：Kimi K2.7 Code 登陆 GitHub Copilot Choice 的首个开放权重模型。Reddit 上讨论聚焦 Agent 的 code bench 性能，K2.7 vs GPT-5.5 vs Claude Opus 4.8 横向对比。

## Qwen (Alibaba) — Qwen3-Coder-Next (arXiv 2603.00729)

链接：arxiv.org/abs/2603.00729

工程范式：极致参数效率 + agentic training 路线——80B 仅 3B 激活。

设计哲学：Qwen 团队的最重要约束是本地开发和低延迟场景。80B 总参但只激活 3B 的 MoE 设计是极致的效率优先选择。为实现 agentic 能力，构建了 MegaFlow 编排系统、合成了约 165 万可验证代码任务实例（~800K 来自真实 PR，~851K 来自合成 bug）。

关键架构决策：
- MoE：80B 总参 / 3B 激活（业界最低的 active parameter ratio）
- attention：hybrid attention（与 Qwen3-Next 保持一致）
- 训练 pipeline：continued pretraining → SFT → specialized experts → distillation
- 合成数据：165 万+ 个可验证代码任务，跨 9+ 编程语言

范式对比：vs Kimi K2.7（1T/32B，超大 MoE），Qwen3-Coder-Next 是另一个极端——用最少的激活参数做编码。3B 激活参数的效率高得离谱，但极限能力不如大模型。

可复用的经验：(1) agentic training 需要可验证的执行环境反馈；(2) 不同 scaffold 间的能力不迁移，需要 scaffold-specific 数据；(3) 最佳拟合打包（BFP）优于简单拼接。

## Zhipu AI — GLM-5 (Feb 2026, arXiv 2602.15763)

链接：z.ai/blog/glm-5

工程范式：系统架构师路线——把 LLM 定位为软件工程和系统架构的自动化工具。

设计哲学：Z.ai 在 GLM-5 中做了几个重要的工程选择。放弃通用对话优化，专注 agentic engineering 和 long-horizon 任务。集成 DeepSeek Sparse Attention (DSA) 降低部署成本。引入 Slime 异步 RL 系统解耦训练和推理。744B 参数但在国产 GPU 上全栈适配——这是实用性的选择，不是技术最优的选择。

关键架构决策：
- MoE：744B 总参 / 40B 激活，256 专家
- Attention：MLA + DSA，支持 200K 上下文
- Training：28.5T tokens pre-training + Slime 异步 RL
- Optimizer：Muon Split（按 attention head 拆分做独立正交化）

范式对比：vs DeepSeek（自研全套，不从别家借），GLM-5 愿意复用 DSA。vs Qwen（持续开源迭代），Z.ai 的迭代周期更长但变化更大（4.7 → 5 的架构差异大）。

## Meta FAIR — Llama 4 Maverick (2025-Q2, 持续迭代)

工程范式：开源生态标杆路线——用开源模型建立使用基数和生态护城河。

设计哲学：Meta 没有发布 Llama 5，持续在 Llama 4 系列上迭代。Maverick 是 400B 总参 / 17B 激活的 MoE 模型，原生多模态。Meta 的主张是：开源模型的 Adoption 比性能数字更重要。这个战略在 ATOM Report（arXiv 2604.07190）的数据中得到验证——Llama、Qwen、DeepSeek 三者占据开源生态的绝大部分下载量和衍生模型数。

关键结果：Llama 4 Maverick 在 AI Index v4.0 上得分约 47-48（vs GLM-5 的 50）。Llama 4 Behemoth（更大版本）仍在训练中，至 2026 年 3 月未公开。

## Mistral — Ministral 3 Series (arXiv 2601.08584)

工程范式：Cascade Distillation 路线——用强母模型蒸馏出小参数高效率的部署模型。

设计哲学：Mistral 的核心约束是小参数模型在部署场景中的性价比优势。Ministral 3 系列（3B/8B/14B）不是从零训练的——它们通过 Cascade Distillation 从 Mistral Small 3.1（24B 母模型）逐层蒸馏而来，训练数据仅 1-3T tokens（vs Qwen3 的 36T 和 Llama3 的 15T）。

关键决策：蒸馏不是一次性操作，而是 cascade 过程——先用母模型生成 soft targets，student 学习，然后 student 再做新 student 的老师。每个层级蒸馏数据量递减。关键放弃：母模型的能力天花板限制了蒸馏模型的上限。

范式对比：vs Qwen（极简激活参数），Mistral 走密集小模型路线。vs DeepSeek（MoE 极致效率），Mistral 认为对部署场景来说蒸馏的性价比高于 MoE。

## OpenAI — GPT-5.5 (Apr 23, 2026)

工程范式：统一推理路线——不再分模型系列，一个模型处理所有类型的推理。

设计哲学：GPT-5.5 不是 GPT-5.x 系列的又一个 post-training 迭代——它是自 GPT-4.5 以来的第一次完整重新训练（full retrain）。1M token 上下文、统一的推理机制（自适应思考深度）、Agent 优先的设计。关键放弃：GPT-5.5 没有做能力分层或安全降级（与 Anthropic 不同），所有用户得到同样的模型能力。

关键结果：AA Intelligence Index v4.0 上 60 分（行业最高），Terminal-Bench 2.0 82.7%。定价 $5/$30 per M token（约 Fable 5 的一半）。

范式对比：vs Anthropic（安全分层），OpenAI 选择统一模型。vs Google（agent 扩展），OpenAI 选择推理深度扩展。
